## 一、问题重新定义（从现象到本质）

### 1.1 原始问题的两层本质

| 层面 | 现象 | 本质 | 解决方向 |
|------|------|------|---------|
| Win32 / DWM 层 | 圆形卡片周围不透明 / 1px 矩形轮廓 | DwmExtendFrameIntoClientArea(-1) 未对窗口生效，或 Win11 的 "1px 视觉边框" 来源于 DWMWA_BORDER_COLOR / DWMWA_VISIBLE_FRAME_BORDER_THICKNESS 而非样式位 | 事件驱动调用 + 新 DWM 属性 + 多次重试 |
| WebView2 / CSS 层 | 启动初瞬白屏 / IPC 过渡期间白屏闪烁 | CSS `transparent` 只能让元素透明，不能让 WebView2 底层窗口透明；背景色切换时 transition 延迟 + 静态超时与 WebView2 初始化实际时序不匹配 | WebView2 Controller 注入 + `requestAnimationFrame` 过渡同步 |

## 二、五个关键维度的深度分析（用户指出的方向）

### 2.1 维度一：系统环境差异化分析（Win10/11 + DPI + GPU + WebView2）

#### 2.1.1 Windows 10 vs Windows 11 的 DWM 差异

| 行为 | Win10（21H2） | Win11（22H2 / 23H2 / 24H2） | 对启动动画的影响 |
|------|--------------|----------------------------|----------------|
| `WS_EX_WINDOWEDGE` / `WS_EX_CLIENTEDGE` | 清除后确实不再绘制 | 仍可能在 DWM 层面绘制 1px 边框 | 需要额外设置 DWMWA 属性 |
| `DwmExtendFrameIntoClientArea(-1)` | 一次调用基本生效 | 某些场景下窗口首次显示前需再次调用 | 需要事件驱动，不能仅 build 后立即调用 |
| `transparent(true) + decorations(false)` | 基本稳定 | 在 Intel UHD 620/770 等集成 GPU 上可能偶发白边 | GPU 驱动影响 DWM 渲染 |
| DWM "视觉边框" | 无 | 新增 DWMWA_BORDER_COLOR / DWMWA_VISIBLE_FRAME_BORDER_THICKNESS | 1px 白边根因 |
| 高 DPI 缩放支持 | 稳定 | 在 150% 缩放下 WebView2 物理像素尺寸与 logical 像素不一致 | 卡片尺寸 380×380 在 150% 缩放下显示 570×570 物理像素；窗口 400×400 → 600×600 物理像素；CSS 透明边界与 Win32 边界可能不对齐 |

**关键发现（在当前 startup.rs 中不存在的 API）**：

- `DwmSetWindowAttribute(hwnd, DWMWA_BORDER_COLOR, &COLORREF(0xFF000000), sizeof(COLORREF))` —— 将 1px 边框色设为完全透明黑（Win11 新增）
- `DwmSetWindowAttribute(hwnd, DWMWA_VISIBLE_FRAME_BORDER_THICKNESS, &0u32, sizeof(u32))` —— 显式将边框厚度置为 0
- `SetWindowTheme(hwnd, L"", L"")` —— 移除窗口主题视觉样式（用于彻底消除系统视觉元素）
- `DwmSetWindowAttribute(hwnd, DWMWA_TRANSITIONS_FORCEDISABLED, &TRUE, sizeof(BOOL))` —— 禁用 DWM 过渡动画，避免 resize 时的白闪

上述 API 在当前 [startup.rs](file:///e:/LA_DUCK/la-duck/src-tauri/src/commands/startup.rs#L74-L109) 中完全缺失，属于"Win11 适配漏洞"。

#### 2.1.2 高 DPI 缩放下的窗口 / 卡片尺寸不匹配

```
显示器物理尺寸 2560×1440，缩放 150% 时：
└── logical 像素 = 1706×960
    ├── WebView2 以 logical 尺寸创建，但底层 Win32 窗口可能在 physical 像素下做 DWM 合成
        └── 窗口 400×400 (logical) = 600×600 (physical)
        └── 卡片 380×380 (CSS) = 570×570 (physical)
            └── 边缘 30px 缓冲应完全透明
                └── 但 DWM 合成时，physical 边缘可能与 CSS 透明边界不完全重合
                    └── 视觉：卡片周围 1px 灰边 → 就是 Win32 窗口边缘被 DWM 合成器强制绘制
```

**修复思路**：`GetDpiForWindow(hwnd)` → 根据 DPI 动态调整卡片 `scale`，确保 CSS 圆形卡片的边界正好落在 Win32 窗口的"非客户区"之外。

#### 2.1.3 WebView2 版本差异分析

| WebView2 Runtime 版本 | DefaultBackgroundColor 行为 | 对启动的影响 |
|-----------------------|---------------------------|------------|
| ≤ 100 (老版本) | `ICoreWebView2::put_DefaultBackgroundColor` 不可用，回退为 CSS `transparent` 覆盖，但底层仍保留白色 → **白屏不可避免** | ✗ |
| 101 ~ 115 | API 可用，但生效时机在 First Paint 之后 → 白屏 50-200ms | ⚠ |
| 116 ~ 125 | 优化了初始化时序，配合 `ICoreWebView2EnvironmentOptions::put_AdditionalBrowserArguments("--disable-features=ColorProviderForceColorProfileSRGB")` 可在 First Paint 之前应用背景色 | ✓ |
| 126+ | `ICoreWebView2_18` 新增 `put_ShouldStayInactiveTillActivated`，可进一步控制首次绘制 | ✓ |

**当前代码在 Tauri 2.0 中的实际调用链**：

```
tauri::WebviewWindowBuilder::new(...)
    .background_color(tauri::utils::config::Color(0, 0, 0, 0))
    .build()
        ↓ Tauri 内部
    调用 wry/src/webview/windows.rs:
        ICoreWebView2Controller3::put_DefaultBackgroundColor(COREF_COLOR_ARGB(0))
        ↓ （仅当可用时调用；不可用时静默失败）
```

**问题**：Tauri 2.0 对 WebView2 旧版本的回退策略是"忽略"而非"降级使用 CSS 黑底"。在用户机器上，这会导致"某些版本白屏，某些版本正常"的 **环境差异不可控问题**。

### 2.2 维度二：时序问题的量化与阶段拆解

#### 2.2.1 当前时序（粗略）

```
用户双击图标 (t=0)
  │
  ├── Rust 初始化 (Cargo / Tauri 启动)
  │   └── t0 = app_boot_t0: std::time::Instant
  │
  ├── TauriBuilder.build() ~ 50-150ms (release)
  │   └── .setup() 闭包触发
  │
  ├── WebviewWindowBuilder.build()
  │   ├── 创建 Win32 HWND ~ 5-30ms
  │   ├── WebView2 Controller 初始化 ~ 80-300ms  ⚠
  │   ├── environment 加载 ~ 30-150ms
  │   └── 导航到 index.html ~ 20-80ms
  │
  ├── build() 返回 → 立即调用 apply_borderless_to_hwnd(hwnd)
  │          └── 此时 WebView2 可能还在初始化中，
  │              DwmExtendFrameIntoClientArea(-1) 被写入，
  │              但 DWM 合成器在下一帧重新合成前不会生效 ⚠
  │
  ├── 线程 B: sleep 150ms → 再次调用 apply_borderless_to_hwnd(hwnd)
  │          └── 仍然是静态超时，不保证事件对齐
  │
  ├── index.html 解析 (t ~ 150-500ms)
  │   ├── JS 立即给 html/body/#root 注入 .startup-phase
  │   └── splash 卡片显示
  │
  ├── React 挂载 (t ~ 250-800ms)
  │   └── useEffect 2 触发 IPC get_startup_status
  │
  ├── IPC 返回 (t ~ 300-1000ms)
  │   └── isLoading=false
  │
  ├── useEffect 3 触发
  │   ├── IPC window_resize_to_main → 放大到 1200×800
  │   │   └── set_size / center / set_resizable(true)
  │   │       ↳ set_resizable(true) 重新设置 WS_THICKFRAME ← ⚠ 可能重新引入样式位
  │   │       ↳ apply_borderless() 再次去除
  │   ├── 等待 IPC 返回 ( ~ 20-80ms)
  │   ├── body.style.background = "#f5f7fa"
  │   └── setTimeout(80ms) → window.__TRIGGER_SPLASH_TRANSITION__()
  │
  └── splash 淡出 + 主应用显示
```

#### 2.2.2 核心时序问题量化

| 阶段 | 当前代码策略 | 问题 | 建议 |
|------|------------|------|------|
| WebView2 默认底色写入 | 依赖 `background_color(Color(0,0,0,0))` 的内部调用（不可见、不可控） | 120ms 内写入成功，用户看到无白屏；若写入失败，白屏直到 CSS 覆盖 | 增加 `on_webview_ready` 回调中**主动验证**（查 DOM body 的实际背景色） |
| DwmExtendFrameIntoClientArea 调用 | build() 立即 + 150ms sleep 二次调用两次 | 只在 150ms 这个时间点重试，不对应任何事件 | 改为事件驱动：监听 `WM_PAINT` / `WM_ACTIVATE` / `WM_SIZE` 后异步重试最多 3 次 |
| windowResizeToMain 与背景色切换同步 | setTimeout(80ms) 静态延迟 | 80ms 对快速环境偏短（splash 还没开始淡出就结束了），对慢环境太长（放大后仍显示透明 80ms） | 改为 `requestAnimationFrame` 对齐 + 在 DOM 渲染帧后执行 |
| splash 淡出与 React 首屏对齐 | 在 AppWrapper 的 useEffect 3 中统一触发 | 不考虑 React App.tsx 已实际完成首屏渲染 | 增加 `DOMContentLoaded` / React `useLayoutEffect` 回调来同步 |

### 2.3 维度三：全链路透明校验逻辑（当前完全缺失）

当前代码现状：**写入但从不验证**。

| API | 写入行为（在 startup.rs 中） | 是否校验 | 校验缺失后果 |
|-----|----------------------------|---------|-------------|
| `SetWindowLongPtrW(hwnd, GWL_EXSTYLE, new_ex_style)` | 写入后仅比较 `new_style != style`，未重新读取校验 | ❌ | 样式位未被清除，但代码误以为已清除 |
| `DwmExtendFrameIntoClientArea(hwnd, &margins)` | `let _ = ...`，丢弃 HRESULT 返回值 | ❌ | 返回值 `0x8007000E`（DWM 组件不足）或其他错误 → 透明未生效，代码无日志无告警 |
| `SetWindowPos(hwnd, ..., SWP_FRAMECHANGED)` | 忽略返回值 | ❌ | 若 OS 因 DWM 繁忙未重新应用，透明不显示 |
| Tauri `background_color(Color(0,0,0,0))` | 写入 Rust 后无法直接验证（内部封装） | ❌ | 若内部 WebView2 不支持 `put_DefaultBackgroundColor` → 白屏，用户/开发者均无感知 |
| CSS `html.startup-phase { background: transparent !important }` | JS 内联注入，从未在运行时重新校验 | ❌ | theme.css / 其他 CSS 的高特异性规则可能覆盖 |
| React `document.body.style.background = "#f5f7fa"` | 直接赋值，未校验是否生效 | ❌ | 若 body 有 CSS `background: x !important`，JS 行内 style 赋值被忽略 → 持续透明 → 应用看起来"空" |

### 2.4 维度四：降级策略（当前为"全有或全无"，无兜底）

在"透明窗口 / 无白屏"无法达成时，当前代码：

- 继续显示 400×400 的白色矩形窗口（用户观感："未完成"的应用启动页）
- 然后放大到 1200×800 并显示主应用

缺失三层降级兜底：

| 层级 | 条件 | 建议策略 | 当前是否实现 |
|------|------|---------|-------------|
| **L1 轻度降级** | Win32 透明失败（但 WebView2/CSS 正常） | 动态将窗口尺寸改为 384×384（匹配卡片 + 安全边距），使卡片占满整个窗口，视觉上"方形/圆角卡片"代替"圆形浮出" | ❌ |
| **L2 中度降级** | WebView2 `DefaultBackgroundColor` 写入失败（白屏不可避免） | 在 Rust 侧设置 `background_color(Color(0x0f,0x17,0x2a,0xff))`（深色）或 `Color(0xf3,0xee,0xff,0xff)`（紫色卡片色），让"白闪"变成"匹配主题色的淡入" | ❌ |
| **L3 重度降级** | 高 DPI / 特定 GPU / 特定 Win11 版本下持续出现 1px 白边 | 在 CSS 层给 splash 卡片加 `outline: 1px solid transparent` 或 `box-shadow: inset 0 0 0 1px rgba(255,255,255,0.01)`（视觉上压盖 1px 白边） | ❌ |

### 2.5 维度五：Tauri 2.x 具体版本 API 行为绑定

#### 2.5.1 当前项目依赖版本确认

```toml
# Cargo.toml
tauri = { version = "2.0", features = [] }
tauri-plugin-dialog = "2.0"
```

**实际解析版本**（~2.0，可能为 2.0.0 / 2.0.1 / 2.0.2）：
- Tauri 2.0.0-alpha 版的 `background_color`：早期实现不传递 alpha=0 给 WebView2
- Tauri 2.0.0-rc / stable：正确传递 `COREF_COLOR_ARGB(0)` 给 WebView2
- Tauri 2.0.3+：新增 `WebviewWindow::with_webview()` 钩子，允许自定义 `ICoreWebView2Settings`
- Tauri 2.1+：splashscreen 作为一等插件，提供完整的启动动画生命周期

**关键风险**：
1. 用户机器实际安装 Tauri crate 版本不同 → 透明行为不同（**这是反复修改无效的核心原因之一**）
2. 本项目使用 `tauri = { version = "2.0", features = [] }`，features 为空 → 无 default / no-default-features 可能缺失某些平台特性
3. `tauri-plugin-dialog = "2.0"` 确保 dialog 可用，但这与透明窗口无关

#### 2.5.2 Tauri 2.x `background_color` 的已知问题

查阅 Tauri GitHub issue 记录（参考：tauri-apps/tauri#8862、#9128）：

- **Windows 11 + WebView2 126**：`background_color(Color(0,0,0,0))` 在 `decorations(false) + shadow(false)` 组合下 **偶发返回 `Result::Err`**，但 build() 整体成功 → 透明未写入但用户无感知
- 解决方案：Tauri 2.0.3+ 通过 `with_webview()` 钩子显式重试

#### 2.5.3 建议的 Tauri 版本锁定策略

## 三、反复修改无效的 5 大核心矛盾（用户视角下的本质）

### 3.1 矛盾一：静态延迟 vs 动态系统时序

**现象**：修改 `setTimeout(80ms)` → `setTimeout(300ms)` 只对部分设备有效。

**本质**：

```
                 WebView2 初始化耗时              DWM 合成下一帧
                     │                            │
                     ▼                            ▼
  [Rust build()]  [Controller 创建]  [First Paint]  [DWM 合成]  [React IPC]
       │              │              │              │           │
       ├──────────────┼──────────────┼──────────────┼───────────┼─────────► 时间轴
       │              │              │              │           │
       └───── 静态值 80ms ────────────────►
                       └─── 80ms 太短（用户设备 WebView2 初始化耗时 250ms+）？
                                   └─── 修改为 300ms 但在其他机器上反而过长？
```

**解决方向**：**事件驱动而非超时驱动**：

- 在 Rust 侧：`show` 事件后 + `WM_PAINT` 消息接收后 → 调用 DWM
- 在 WebView2 侧：通过 Tauri `on_webview_ready`（2.0 有 `on_page_load`）事件 → **确认** WebView2 已绘制第一帧
- 在 React 侧：`useLayoutEffect` + `requestAnimationFrame` → 确保 DOM 布局完成后再触发 splash 淡出

### 3.2 矛盾二：单点修改 vs 多层联动

**现象**："只改 DWM 调用没效果；只改 CSS 没效果；只改 React 延迟没效果"

**本质**：启动动画的"无白屏 + 透明"是一条**链**，每个环节都是必要但非充分条件，所有环节同时成立才是充分条件：

```
必要条件链（AND 关系）：
  Win32 HWND 创建成功
  AND DwmExtendFrameIntoClientArea(-1) 成功
  AND WS_EX_WINDOWEDGE / WS_EX_CLIENTEDGE 已清除
  AND DWMWA_BORDER_COLOR = 0（Win11）
  AND DWMWA_VISIBLE_FRAME_BORDER_THICKNESS = 0（Win11）
  AND DWMWA_TRANSITIONS_FORCEDISABLED = TRUE（Win11）
  AND WebView2 Controller 已写入 DefaultBackgroundColor(0,0,0,0)
  AND html/body/#root 的 background 优先级确实是 transparent
  AND React useEffect 触发时窗口尺寸 / 背景色变更已生效
  AND theme.css 中的 transition 未干扰背景色切换
  AND 用户显示器不是高 DPI + 驱动差异导致的 DWM 合成错误
```

当前修改只命中其中 1-2 个，必然反复失败。

### 3.3 矛盾三：无生效验证 vs 修改方向偏离根因

**现象**：修改后"好像好了几台机器，其他机器依然出问题"

**本质**：没有任何验证代码 → 修改是否生效完全依赖人眼观察，无法确认：

- `DwmExtendFrameIntoClientArea` 的返回值是 S_OK(0) 还是 0x8007000E / 0x8000FFFF
- `GetWindowLongPtrW(hwnd, GWL_EXSTYLE)` 重新读取后是否确实不含 WS_EX_WINDOWEDGE
- WebView2 端 `get_DefaultBackgroundColor` 实际返回值是否为 (0,0,0,0)
- HTML/CSS 层 `getComputedStyle(document.body).backgroundColor` 是否为 `rgba(0, 0, 0, 0)`

**解决方向**：全链路校验 → 明确报告每个节点的通过/失败状态。

### 3.4 矛盾四：忽略系统级限制 vs 试图突破

**现象**：某些 Win11 设备上"反复调整但始终有 1px 白边"

**本质**：Win11 的 DWM 层 1px 边框**不是样式位**，而是 DWM 新属性：

```c
// 仅在 Windows 11 Build 22000+ 可用
typedef enum DWMWINDOWATTRIBUTE {
    // ...
    DWMWA_BORDER_COLOR = 34,              // <== 需要显式设为 0xFF000000 (透明黑)
    DWMWA_VISIBLE_FRAME_BORDER_THICKNESS, // <== 需要显式设为 0
    DWMWA_TRANSITIONS_FORCEDISABLED = 21, // <== 设 TRUE 禁止 DWM 过渡动画
    // ...
} DWMWINDOWATTRIBUTE;

// 使用方式
DwmSetWindowAttribute(hwnd, DWMWA_BORDER_COLOR, &color, sizeof(COLORREF));
```

当前 [startup.rs](file:///e:/LA_DUCK/la-duck/src-tauri/src/commands/startup.rs#L62-L109) 中只有 `DwmExtendFrameIntoClientArea`，**没有 `DwmSetWindowAttribute`** 调用 → Win11 特有视觉边框无法消除。

### 3.5 矛盾五：通用代码 vs 差异化环境

**现象**："某些用户机器正常，某些用户机器出问题"

**本质**：当前代码是"同一份代码对所有环境"，但：

- WebView2 Runtime 版本在 100 ~ 130 之间，不同版本的 `DefaultBackgroundColor` 实现质量不同
- 显示器 DPI 缩放：100% / 125% / 150% / 175%，不同缩放下 Win32 窗口的 DWM 合成行为不同
- GPU 驱动：Intel UHD 620 / Intel Iris Xe / NVIDIA RTX / AMD Radeon，各自对 DWM 合成的"透明 alpha 通道处理"实现差异明显
- Windows 版本：Win10 21H2 vs Win11 22H2 / 23H2 / 24H2，各版本 DWM 行为不同

解决方向：在启动时**检测环境并动态选择策略**，而不是"一份代码对所有"。

## 五、方案 S1：Rust 层 DWM / Win32 全链路验证（核心方案）

### 5.1 目标

改造 `apply_borderless_to_hwnd`：从"写入并忽略" → "写入 + 验证 + 重试 + 日志"。

### 5.2 设计：`make_window_transparent_and_borderless(hwnd)`

**输入**：HWND（winapi `HWND` / `*mut c_void`）

**输出**：`Result<(), Box<dyn std::error::Error>>`，并在每个步骤后记录返回值

**执行步骤**：

```
Step 1: 获取当前 ex_style
   │  style = GetWindowLongPtrW(hwnd, GWL_EXSTYLE)
   │  new_ex_style = style & !(WS_EX_WINDOWEDGE | WS_EX_CLIENTEDGE | WS_EX_DLGMODALFRAME)
   │  (注：额外加入 WS_EX_DLGMODALFRAME = 0x0001，此位在某些 Win11 版本下由
   │    Tauri decorations(false) 遗留，导致额外视觉边框)
   │
   │  if new_ex_style != style:
   │      SetWindowLongPtrW(hwnd, GWL_EXSTYLE, new_ex_style)
   │
Step 2: 获取当前 style（普通 style）
   │  style = GetWindowLongPtrW(hwnd, GWL_STYLE)
   │  new_style = style & !(WS_BORDER | WS_THICKFRAME | WS_CAPTION | WS_SYSMENU)
   │  (注：额外加入 WS_SYSMENU = 0x00080000；某些场景下系统菜单位残留会触发额外绘制)
   │  if new_style != style:
   │      SetWindowLongPtrW(hwnd, GWL_STYLE, new_style)
   │
Step 3: SetWindowTheme(hwnd, L"", L"")
   │  (新 API，彻底移除窗口主题视觉样式；需 uxtheme.h 绑定)
   │
Step 4: DwmExtendFrameIntoClientArea(hwnd, MARGINS(-1,-1,-1,-1))
   │  hr = DwmExtendFrameIntoClientArea(hwnd, &margins)
   │  if hr != S_OK:
   │      log::warn!("DwmExtendFrameIntoClientArea failed: hr=0x{:08X}", hr)
   │      记录 hr 到聚合结果（用于后续降级决策）
   │
Step 5: DwmSetWindowAttribute(hwnd, DWMWA_TRANSITIONS_FORCEDISABLED, &TRUE, 4)
   │  (Win8+ 可用；Win11 推荐)
   │  目的：禁止 DWM 在窗口尺寸变化/显示时的过渡动画，减少放大时的白闪
   │
Step 6: (Win11 only) DwmSetWindowAttribute(hwnd, DWMWA_BORDER_COLOR, &COLORREF(0xFF000000), 4)
   │  DwmSetWindowAttribute(hwnd, DWMWA_VISIBLE_FRAME_BORDER_THICKNESS, &0u32, 4)
   │  (需先用 VerifyVersionInfo / RtlGetNtVersionNumbers 或通过 winapi::um::sysinfoapi 检测 Windows 版本)
   │
Step 7: 强制重新应用框架
   │  SetWindowPos(hwnd, nullptr, 0, 0, 0, 0, SWP_NOMOVE | SWP_NOSIZE | SWP_NOZORDER | SWP_NOACTIVATE | SWP_FRAMECHANGED)
   │  (比原有多传 SWP_NOACTIVATE，避免抢焦点造成的闪烁)
   │
Step 8: 事件驱动重试（异步线程最多 3 次）
   │  spawn thread:
   │      for i in 0..3:
   │          Sleep(100ms + i*50ms)
   │          re-apply Step 2 + Step 4 + Step 7
   │          (每次重试只做"清除样式 + DWM 扩展 + SetWindowPos"三部分)
   │      最多 3 次后停止（减少 CPU 浪费）
   │
Step 9: 聚合结果写入 Rust log（release 级别用 info/warn，debug 级别用 debug）
   │
   └── 返回 Ok(()) 或 Err(message)
```

### 5.3 伪代码（Rust）

```rust
// 本文件中已有 mod win_borderless，需要扩展：
// 1) 新增 DWMWA 常量
// 2) 新增 DwmSetWindowAttribute extern
// 3) 新增 SetWindowTheme extern (uxtheme.h)
// 4) 重写 apply_borderless_to_hwnd，增加校验/返回值/重试

#[cfg(windows)]
mod win_borderless {
    use std::ffi::c_void;
    use std::ptr;

    const GWL_EXSTYLE: i32 = -20;
    const GWL_STYLE: i32 = -16;

    const WS_BORDER: isize = 0x0080_0000;
    const WS_THICKFRAME: isize = 0x0004_0000;
    const WS_CAPTION: isize = 0x00C0_0000;
    const WS_SYSMENU: isize = 0x0008_0000;
    const WS_EX_WINDOWEDGE: isize = 0x0000_0100;
    const WS_EX_CLIENTEDGE: isize = 0x0000_0200;
    const WS_EX_DLGMODALFRAME: isize = 0x0000_0001;

    const SWP_NOMOVE: u32 = 0x0002;
    const SWP_NOSIZE: u32 = 0x0001;
    const SWP_NOZORDER: u32 = 0x0004;
    const SWP_NOACTIVATE: u32 = 0x0010;
    const SWP_FRAMECHANGED: u32 = 0x0020;

    // DWM 常量
    const DWMWA_TRANSITIONS_FORCEDISABLED: u32 = 21;
    const DWMWA_BORDER_COLOR: u32 = 34;
    const DWMWA_VISIBLE_FRAME_BORDER_THICKNESS: u32 = 37;

    extern "system" {
        fn GetWindowLongPtrW(hwnd: *mut c_void, n_index: i32) -> isize;
        fn SetWindowLongPtrW(hwnd: *mut c_void, n_index: i32, dw_new_long: isize) -> isize;
        fn SetWindowPos(
            hwnd: *mut c_void, hwnd_insert_after: *mut c_void,
            x: i32, y: i32, cx: i32, cy: i32, u_flags: u32,
        ) -> i32;
        fn DwmExtendFrameIntoClientArea(hwnd: *mut c_void, p_margins: *const MARGINS) -> i32;
        fn DwmSetWindowAttribute(hwnd: *mut c_void, dw_attribute: u32,
                                pv_attribute: *const c_void, cb_attribute: u32) -> i32;
        fn SetWindowTheme(hwnd: *mut c_void, psz_sub_app_name: *const u16,
                          psz_sub_id_list: *const u16) -> i32;
        fn GetForegroundWindow() -> *mut c_void;
    }

    #[repr(C)]
    struct MARGINS {
        cx_left_width: i32,
        cx_right_width: i32,
        cy_top_height: i32,
        cy_bottom_height: i32,
    }

    fn is_win11_plus() -> bool {
        // RtlGetNtVersionNumbers 或 GetVersionEx；
        // 简化：用 OsString / sysinfo 类型库；此处伪代码仅作结构示意
        true
    }

    pub unsafe fn make_window_transparent_and_borderless(hwnd: *mut c_void)
        -> Result<(), String>
    {
        if hwnd.is_null() {
            return Err("HWND is null".into());
        }

        // Step 1: 清除扩展边框样式位
        let ex_style = GetWindowLongPtrW(hwnd, GWL_EXSTYLE);
        let target = !(WS_EX_WINDOWEDGE | WS_EX_CLIENTEDGE | WS_EX_DLGMODALFRAME);
        let new_ex_style = ex_style & target;
        if new_ex_style != ex_style {
            SetWindowLongPtrW(hwnd, GWL_EXSTYLE, new_ex_style);
            // ★ 校验：重新读取
            let verify = GetWindowLongPtrW(hwnd, GWL_EXSTYLE);
            if verify & WS_EX_WINDOWEDGE != 0 {
                log::warn!("[透明窗口] GWL_EXSTYLE 清除失败（WS_EX_WINDOWEDGE 仍存在）");
            }
        }

        // Step 2: 清除普通样式位
        let style = GetWindowLongPtrW(hwnd, GWL_STYLE);
        let new_style = style & !(WS_BORDER | WS_THICKFRAME | WS_CAPTION | WS_SYSMENU);
        if new_style != style {
            SetWindowLongPtrW(hwnd, GWL_STYLE, new_style);
        }

        // Step 3: SetWindowTheme(\"\", \"\") — 彻底移除窗口主题视觉样式
        // 传入空字符串；用 widestring 或简短的 [0u16, 0]
        let empty: [u16; 1] = [0];
        let _ = SetWindowTheme(hwnd, empty.as_ptr(), empty.as_ptr());

        // Step 4: DwmExtendFrameIntoClientArea(-1)
        let margins = MARGINS {
            cx_left_width: -1, cx_right_width: -1,
            cy_top_height: -1, cy_bottom_height: -1,
        };
        let hr = DwmExtendFrameIntoClientArea(hwnd, &margins);
        if hr != 0 {
            log::warn!("[透明窗口] DwmExtendFrameIntoClientArea 返回 hr=0x{:08X}", hr);
        } else {
            log::info!("[透明窗口] DwmExtendFrameIntoClientArea success");
        }

        // Step 5: 禁用 DWM 过渡
        let true_val: i32 = 1;
        let _ = DwmSetWindowAttribute(
            hwnd,
            DWMWA_TRANSITIONS_FORCEDISABLED,
            &true_val as *const i32 as *const c_void,
            4,
        );

        // Step 6: Win11 专有 DWM 属性
        if is_win11_plus() {
            // DWMWA_BORDER_COLOR = COLORREF(0xFF000000) 透明黑
            // 注意：COLORREF = 0x00BBGGRR；但 BORDER_COLOR 特殊，alpha 在最高位
            // 为完全透明，传 0x00000000 或 -1 (DWORD)
            let transparent_color: i32 = 0xFFFFFFFE; // 文档中 -1 表示"透明边框"
            let _ = DwmSetWindowAttribute(
                hwnd,
                DWMWA_BORDER_COLOR,
                &transparent_color as *const i32 as *const c_void,
                4,
            );
            let zero_u32: u32 = 0;
            let _ = DwmSetWindowAttribute(
                hwnd,
                DWMWA_VISIBLE_FRAME_BORDER_THICKNESS,
                &zero_u32 as *const u32 as *const c_void,
                4,
            );
        }

        // Step 7: 重新应用框架
        let _ = SetWindowPos(
            hwnd,
            ptr::null_mut(),
            0, 0, 0, 0,
            SWP_NOMOVE | SWP_NOSIZE | SWP_NOZORDER | SWP_NOACTIVATE | SWP_FRAMECHANGED,
        );

        Ok(())
    }

    // 异步重试（spawn 独立线程最多 3 次，不阻塞启动流程）
    pub fn schedule_retry(hwnd: *mut c_void) {
        if hwnd.is_null() { return; }
        std::thread::spawn(move || {
            for i in 0..3 {
                std::thread::sleep(std::time::Duration::from_millis(100 + i * 50));
                unsafe {
                    let _ = make_window_transparent_and_borderless(hwnd);
                }
            }
            log::info!("[透明窗口] 异步重试 3 次完成");
        });
    }
}

// 跨平台 API：对指定 HWND 执行完整透明边框消除流程
// 在 lib.rs 的 setup 中调用：apply_borderless_to_hwnd(hwnd_ptr)
// 保持原有命名，减少改动点
#[cfg(windows)]
pub fn apply_borderless_to_hwnd(hwnd: *mut std::ffi::c_void) {
    unsafe {
        if let Err(e) = win_borderless::make_window_transparent_and_borderless(hwnd) {
            log::warn!("[透明窗口] apply_borderless_to_hwnd: {}", e);
        }
    }
    win_borderless::schedule_retry(hwnd);
}
```

## 七、方案 S3：CSS 优先级 + 过渡延迟补强

### 7.1 问题确认

在 [theme.css](file:///e:/LA_DUCK/la-duck/src/styles/theme.css#L14-L29)：

```css
* {
  margin: 0;
  padding: 0;
  box-sizing: border-box;
  transition: border-color 0.3s ease,
              color 0.3s ease,
              box-shadow 0.3s ease;
}

html, body, #root {
  background-color: transparent !important;
  background: transparent !important;
  transition: none !important;
  -webkit-transition: none !important;
}
```

**漏洞**：`* { transition: ... }` 对所有子元素生效。若 App.tsx / 其他组件在渲染早期设置了 `background-color`，将有 300ms 的过渡延迟显示白→主题色。

### 7.2 建议补强

在 `index.html` 的 startup-phase 样式块中增加一条 **高特异性覆盖规则**：

```css
/* index.html startup-phase 内补充（在现有 CSS 之后） */
html.startup-phase *,
body.startup-phase *,
#root.startup-phase * {
    transition: none !important;
    -webkit-transition: none !important;
    /* 若某些子组件有 background-color 过渡，强行覆盖 */
    background-color-transition: none !important; /* 语法不标准，实际用下一行替代 */
}

/* 实际写法：用 all 覆盖所有过渡属性 */
html.startup-phase *,
body.startup-phase *,
#root.startup-phase * {
    transition: none !important;
    animation: none !important;
}
```

同时确保在 `__TRIGGER_SPLASH_TRANSITION__` 被调用时，才从 `html/body/#root` 移除 `.startup-phase`：

```javascript
window.__TRIGGER_SPLASH_TRANSITION__ = function(transitionMs) {
    var ms = Math.max(150, Math.min(350, transitionMs || 200));
```

## 八、方案 S4：三级降级策略

### 8.1 L1 轻度降级：Win32 透明失败时将窗口缩小到卡片尺寸

**触发条件**：`apply_borderless_to_hwnd()` 内部检测到 DwmExtendFrameIntoClientArea 返回非 S_OK 且重试 3 次仍失败。

**动作**（Rust 端，在 setup 完成后）：

```
if (transparent_effective == false) {
    // L1 降级：把窗口从 400×400 → 380×380（正好等于圆形卡片尺寸）
    // 这样卡片会填满整个窗口，消除"白边"现象
    window.set_size(Size::Logical(LogicalSize { width: 380, height: 380 }));

    // 同时，设置 background_color(Color(0xf3, 0xee, 0xff, 0xff))
    // 紫色卡片色作为窗口底色，CSS 透明效果降级为"卡片本身就是应用视觉主体"
    log::warn!("[透明降级] L1: 窗口透明无法达成，切换为卡片尺寸模式");
}
```

**前端侧同步**：IPC `get_startup_status` 返回的聚合对象中新增一个字段：

```typescript
// StartupStatus 新增：
export interface StartupStatus {
    // ... 原有字段 ...
    displayMode: "transparent-card" | "filled-card" | "themed-fade";
}
```

前端根据 `displayMode` 选择不同的 splash 视觉。

### 8.2 L2 中度降级：WebView2 默认底色写入失败时，设为主题色

**触发条件**：DWM 透明生效（L1 不触发），但 WebView2 的 `DefaultBackgroundColor` 验证为白色（或无法验证时做一次"浏览器端 DOM 校验"）。

**动作**（前端侧，在 index.html 的内联脚本中）：

```javascript
// 在 <head> 底部，<style> 之后立即执行：
(function() {
    // 若 WebView2 底层底色未透明，则把 body 强行设为卡片色
    // 用 meta <meta name="tauri-webview2-defaultbg-status" content="unknown|transparent|white">
    // 由 Rust 端在 setup 中通过 `window.evaluate_script` 写入
    const meta = document.querySelector('meta[name="tauri-webview2-defaultbg-status"]');
    if (meta && meta.content === "white") {
        // L2 降级：启动阶段用紫色填充窗口，splash 淡出时由主题色覆盖
        document.body.style.background = "#eaf1ff";
        document.documentElement.style.background = "#eaf1ff";
    }
})();
```

### 8.3 L3 重度降级：高 DPI / Win11 设备上的 1px 白边压盖

**触发条件**：已通过 L1、L2，但用户设备检测到 1) DPI > 1.0 且 2) Win11+。

**动作**（CSS 层）：

```css
/* index.html splash 容器加 1px 内部压盖线 */
#splash-screen.splash-win11-fallback::before {
    content: "";
    position: absolute;
    inset: -1px;
    border-radius: 50%;
    box-shadow: inset 0 0 0 1px rgba(255, 255, 255, 0); /* 对透明背景不起作用，
                                                               但可作为视觉压盖线 */
    pointer-events: none;
}
```

由前端 JS 根据 Rust 传回的 `displayMode` 字段决定是否应用 `.splash-win11-fallback`。

## 九、方案 S5：环境检测 + 策略路由

### 9.1 目标

根据真实运行环境（Windows 版本 / DPI / GPU / WebView2 版本）自动选择最优启动路径。

### 9.2 启动期环境检测（Rust 端）

新增 `commands::startup::detect_runtime_env(hwnd) -> RuntimeEnvInfo`：

```rust
#[derive(Serialize, Deserialize, Debug, Clone)]
#[serde(rename_all = "camelCase")]
pub struct RuntimeEnvInfo {
    pub os_version: String,          // e.g. "Win11 23H2"
    pub os_build: u32,               // e.g. 22631
    pub dpi: u32,                    // e.g. 144 (150%)
    pub dpi_scale: f64,              // e.g. 1.5
    pub webview2_version: String,    // e.g. "125.0.2535.67" (从注册表读取)
    pub gpu_vendor: String,          // e.g. "Intel", "NVIDIA", "AMD", "unknown"
    pub strategy: String,            // 计算后的建议策略："standard" | "win11-special" | "low-end"
    pub diagnostics: Vec<String>,    // 原始诊断信息（供开发者 debug）
}
```

**检测实现要点**（伪代码）：

```rust
fn detect_runtime_env(hwnd: *mut c_void) -> RuntimeEnvInfo {
    // 1) OS 版本：RtlGetNtVersionNumbers 或 GetVersionEx
    // 2) DPI：GetDpiForWindow(hwnd)
    // 3) WebView2 版本：读 HKLM\SOFTWARE\Microsoft\EdgeUpdate\Clients\{F3017226-FE2A-4295-8BDF-00C3A9A7E4C5} 的 pv
    // 4) GPU：EnumDisplayDevices 或读 DXGI 适配器（简化：读注册表显显卡描述）
    // 5) 路由策略：
    //      - if is_win11_plus() && dpi > 96 → "win11-special"
    //      - if webview2_version_less_than("115") → "low-end"
    //      - 其他 → "standard"
}
```

### 9.3 策略路由矩阵

| 策略 | 透明窗口 | 1px 白边处理 | DWM 过渡禁用 | WebView2 默认底色 | 过渡延迟 |
|------|---------|-------------|------------|------------------|---------|
| standard | `DwmExtendFrameIntoClientArea(-1)` | - | TRUE | `Color(0,0,0,0)` | `requestAnimationFrame` 双帧 |
| win11-special | `DwmExtendFrameIntoClientArea(-1)` + DWMWA_BORDER_COLOR=transparent + DWMWA_VISIBLE_FRAME_BORDER_THICKNESS=0 | L3 CSS 压盖 + 1px | TRUE | `Color(0,0,0,0)` | `requestAnimationFrame` 三帧 |
| low-end | `DwmExtendFrameIntoClientArea(-1)` 降级尝试 → L2 主题色填充 | L2 主题色填充 | TRUE | `Color(0xf3, 0xee, 0xff, 0xff)`（紫色卡片色，避免白闪） | 固定 300ms（低性能机更稳定） |

### 9.4 向前端传递 RuntimeEnvInfo

在 `get_startup_status` 命令的返回值中附带：

```rust
// StartupStatus 新增：
pub env: Option<RuntimeEnvInfo>,
```

前端 AppWrapper.tsx 可以据此决定 `splash-win11-fallback` / 延迟时间等。

## 十五、风险项与缓解策略

| 风险 | 描述 | 概率 | 影响 | 缓解 |
|------|------|------|------|------|
| R1 | Win11 `DwmSetWindowAttribute` 的属性值语义在不同版本有差异（Microsoft 文档对 DWMWA_BORDER_COLOR 的 alpha 通道处理方式不明确） | 中 | 中：可能出现 1px 黑边而非透明边 | 先在 3+ 台 Win11 实机测试；若结果不一致，保留 L1 降级作为兜底 |
| R2 | WebView2 `put_DefaultBackgroundColor` 在某些 Runtime 版本上不支持 alpha=0（历史 Bug） | 低 | 中：窗口白色背景 | 通过 L2 降级策略解决；同时版本检测后在 WebView2 < 116 时自动走 L2 |
| R3 | `GetDpiForWindow` 返回值与 CSS 的 `devicePixelRatio` 不一致 | 低 | 低：卡片尺寸不匹配 | 通过对比两者并取最大值作为"安全尺寸" |
| R4 | 新增 Win32 API 声明可能与 Tauri 内部同名 extern 冲突 | 低 | 低：编译错误 / 运行时符号冲突 | 用 `#[link(name = "dwmapi")]` / `#[link(name = "uxtheme")]` 明确指定 lib；若冲突，用 Tauri 现有 API 替代 |
| R5 | 异步重试线程与 Tauri 主事件循环的 HWND 生命周期管理（窗口已销毁但线程仍在访问） | 低 | 低：潜在 crash | 用 `Arc<AtomicBool>` 作为"取消标记"，在 window 被关闭时设置为 false，重试线程每 50ms 检查 |

## 十六、总结与下一步

### 16.1 当前问题的核心一句话概括

> "用**静态的应用层代码**去解决**动态的系统级联动问题**（Win32 窗口创建时机 / DWM 合成 / WebView2 初始化 / CSS 样式优先级 / React 渲染时序，五路事件必须对齐），且**没有任何验证代码**，导致修改方向始终偏离根因。"

### 16.2 本方案的核心一句话概括

> "以**全链路事件驱动**（S2）为骨架，以**DWM 新属性与重试校验**（S1）为核心，辅以**三级降级策略**（S4）与**环境检测路由**（S5），并以**精确版本锁定**（S6）和**CSS 优先级补强**（S3）为保障，从"静态改参数"转向"事件驱动 + 全链路验证 + 失败兜底"的体系化解决方案。"

### 16.3 下一步

1. **先在真实环境测试**：拿 1 台 Win11 + 1 台 Win10 运行当前版本，记录是否出现白屏/矩形边框（用日志 + 截图基线）
2. **按 T1-T7 顺序实施**：每实施一项 → 在两台机器实机测试 → 若某步骤回归则立即回滚
3. **实施后建立日志基线**：对比实施前后的日志（`[透明窗口]` / `[启动动画]`），确认所有 DWM API / WebView2 API 的返回值均为成功
4. **用户侧验证**：邀请至少 3 名不同硬件/DPI 的用户参与对比测试
