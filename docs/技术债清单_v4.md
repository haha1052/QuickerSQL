## 二、P1 级技术债（3 项，高危）🔴 本版新增

### P1-1 | Rust 工具链损坏，编译与测试门禁全线失效 🔴

- **发现时间**: 2026-10-20
- **现象**:
  ```
  $ cargo test --quiet
  error: process didn't exit successfully: `rustc -vV` (exit code: 1)
  error: missing manifest in toolchain 'stable-x86_64-pc-windows-msvc'
  help: this may happen if the toolchain installation was interrupted
  ```
- **根因**: `~/.rustup/toolchains/stable-x86_64-pc-windows-msvc/` 目录**缺失 `rustc` 组件**。实测该目录 `bin/` 下只有 `cargo.exe` / `cargo-clippy.exe` / `clippy-driver.exe` / `rustfmt.exe`，`lib/rustlib/` 下只有 3 个 manifest + `components`，**无 `rust-std` / `rustc` 二进制**。属于工具链安装被中断（磁盘操作、杀毒软件锁文件、异常断电均可能触发）。
- **影响（严重）**:
  - `cargo check --quiet` 无法执行 → **编译门禁形同虚设**
  - `cargo test --quiet` 无法执行 → **393 个 Rust 测试全部无法验证**（是否为绿未知）
  - `npm run tauri dev` / `build` 无法编译 Rust 侧 → **应用无法构建**
  - 文档中所有「✅ cargo check 0 errors / cargo test 393 passed」结论，**自 2026-08-29 起未经复验**
- **修复动作**: `rustup toolchain install stable --profile minimal`
- **修复阻碍（实测）**: 2026-10-20 两次重装均失败，错误为
  ```
  error: could not rename 'component' file from '...\tmp\bk'
    to '...\toolchains\stable-x86_64-pc-windows-msvc\share': 目录不是空的。(os error 145)
  error: component download failed for rust-std-x86_64-pc-windows-msvc (os error 2)
  ```
  → **这是 rustup 并发 rename 与残留目录冲突的已知问题**，非网络问题。
- **建议修复步骤**:
  1. 关闭所有占用该工具链的进程（IDE / cargo / rust-analyzer / Tauri dev server）
  2. 删除残留目录：`rm -rf ~/.rustup/toolchains/stable-x86_64-pc-windows-msvc`（若被占用，先结束 rust-analyzer）
  3. 清理下载缓存：`rm -rf ~/.rustup/downloads ~/.rustup/tmp`
  4. 重装：`rustup toolchain install stable --profile default`
  5. 验证：`rustc --version && cargo --version && cd src-tauri && cargo test`
- **验收**: `cargo check --quiet` 与 `cargo test --quiet` 均能正常执行并给出结果
- **附加建议**: 在 `scripts/` 增加 `check-toolchain.mjs`，CI 与本地提交前先跑 `rustc --version`，工具链缺失时**立即失败**而非静默跳过

### P1-3 | 质量门禁缺少「工具链可用性」与「严格 i18n」两道检查

- **问题描述**: 现有门禁脚本（`check-doc-sync.ps1` / `scan-hardcoded.mjs`）存在两个盲区：
  1. **不检查 `rustc` 是否可用** —— P1-1 发生后，所有 cargo 相关门禁静默失效长达 1 个多月无人发现
  2. **i18n 检测用宽松脚本** —— P1-2 发生后，门禁长期报「0 处」假绿
- **影响**: 质量基线形同虚设；文档中的 ✅ 结论可能长期停留在过期状态
- **建议修复**: 建立 `npm run check:all` 统一入口，串联：
  ```
  1. rustc --version（工具链可用性，失败即中断）
  2. cargo check --quiet
  3. cargo test --quiet
  4. npx tsc --noEmit --pretty
  5. npx vitest run
  6. node scripts/check-hardcoded-i18n.mjs（严格版）
  7. pwsh scripts/check-doc-sync.ps1
  ```
  任一失败即返回非 0 退出码。

### P2-4 | trash_service.rs 存在「假分支」：Parquet 策略从未真正实现

- **位置**: `src-tauri/src/services/trash_service.rs:94-101`（策略判定）+ `:144-148`（执行分支）
- **问题描述**:
  ```rust
  // L95-101：行数超阈值时返回 Parquet
  pub fn determine_strategy(conn: &MutexGuardConnection<'_>, row_count: u64) -> TrashStrategy {
      let threshold = Self::get_large_table_threshold(conn);
      if row_count > threshold { TrashStrategy::Parquet } else { TrashStrategy::Rename }
  }

  // L144-148：Parquet 分支实际回退到 rename
  TrashStrategy::Parquet => {
      log::info!("表 {} 较大（{} 行），暂时使用重命名策略", table_name, row_count);
      // TODO：Parquet 策略实现
      Self::move_by_rename(...)   // ← 与 Rename 分支完全相同的调用
  }
  ```
- **根因**: `Cargo.toml` **无 parquet 依赖**，Parquet 策略从未实现
- **影响**:
  - 大表回收站**并未**按设计做 Parquet 冷存储，仍走重命名 —— 大表删除后磁盘空间不会真正释放
  - `determine_strategy` 返回 `Parquet` 但执行层无对应能力，属**静默降级**，日志只写 `info` 不写 `warn`，用户无感知
  - 设置项「回收站大表阈值」形同虚设
- **建议修复（二选一）**:
  1. **短期**：在 `determine_strategy` 中直接短路 —— 超阈值时返回 `TrashStrategy::Rename` 并把日志级别提到 `warn`，让「阈值」设置项明确失效或删除
  2. **长期**：真正实现 Parquet 策略（`COPY TO 'x.parquet'` + 删除原表 + 元数据指向文件）
- **建议归入**: 走 spec 流程评估，优先级介于 P2/P3 之间
