## 一、项目概述

### 1.1 什么是 QuickerSQL？

**QuickerSQL** 是一个**本地桌面端数据分析与可视化工具**，让用户可以：
- 📊 通过 SQL 查询分析本地数据
- 📈 创建交互式图表和仪表盘
- 🤖 设置自动化任务（定时查询、数据刷新等）
- 🔒 所有数据存储在本地，保证安全性

### 1.2 核心特点

| 特点 | 说明 |
|------|------|
| **本地优先** | 所有数据存储在用户本地，无需联网 |
| **双引擎** | SQLite（事务处理）+ DuckDB（分析查询） |
| **跨平台** | 基于 Tauri 2，支持 Windows/macOS/Linux |
| **高性能** | 查询缓存、虚拟滚动、代码分割等优化 |
| **可扩展** | 清晰的架构分层，便于添加新功能 |

### 3.2 架构分层说明

#### 前端三层架构

```
components/     ← UI 组件（只读访问 services/）
     │
     ▼
store/          ← 状态管理（组件状态、应用状态）
     │
     ▼
services/       ← 通信封装（invokeCommand<T>() 统一封装）
     │
     ▼
Tauri IPC       ← 前后端通信桥梁
```

#### 后端三层架构

```
commands/       ← 仅做：参数校验 + Service 调用 + 结果包装
     │
     ▼
services/       ← 编排业务流程、事务边界、SQL 仅用参数化查询
     │
     ▼
database/       ← 连接管理、SqlIdentifier 安全封装
     │
     ▼
models/         ← 数据结构定义（零业务逻辑、零数据库连接）
```

### 3.3 数据流向

**查询执行流程**（以 SQL 查询为例）：

1. 用户在 UI 输入 SQL → 点击"执行"
2. `SqlQueryPage.tsx` 调用 `queryStore.executeSql(sql)`
3. `queryStore` 通过 `tauriService.invokeCommand('execute_sql', { sql })`
4. Tauri IPC 调用后端 `commands/sql.rs::execute_sql()`
5. `commands/sql.rs` 校验参数 → 调用 `services/sql_service.rs::execute()`
6. `sql_service.rs` 判断 SQL 类型：
   - 如果是 `SELECT/PRAGMA/WITH` → 走 DuckDB（分析引擎）
   - 如果是 `INSERT/UPDATE/DELETE` → 走 SQLite（事务引擎）
   - 如果是只读语句 → 先查缓存（`query_cache_service.rs`）
7. 执行结果返回 → 逐层包装 → 返回前端
8. 前端更新 `queryStore` → UI 重新渲染显示结果

## 五、关键设计决策

### 5.1 为什么选择双引擎（SQLite + DuckDB）？

| 引擎 | 优势 | 适用场景 |
|------|------|----------|
| **SQLite** | 事务支持好、写入快、成熟稳定 | 日常操作（INSERT/UPDATE/DELETE）、系统表管理 |
| **DuckDB** | 分析查询快、列式存储、SQL 兼容性好 | 复杂查询（SELECT/JOIN/GROUP BY）、大数据量分析 |

**决策**: 根据 SQL 语句类型自动路由：
- `SELECT/PRAGMA/WITH` → DuckDB
- `INSERT/UPDATE/DELETE/CREATE/DROP` → SQLite

### 5.2 为什么采用三层架构（commands → services → database）？

**目标**: 职责清晰、易于测试、便于维护

| 层级 | 职责 | 禁止事项 |
|------|------|----------|
| **commands** | 参数校验、调用 service、包装结果 | ❌ 禁止直接连接数据库 |
| **services** | 业务逻辑编排、事务管理、SQL 构造 | ❌ 禁止处理 HTTP 请求 |
| **database** | 连接管理、SQL 执行、结果映射 | ❌ 禁止业务逻辑判断 |

### 5.3 为什么系统表要用 `__` 前缀？

**目标**: 避免系统表与用户表混淆

| 前缀 | 类型 | 示例 |
|------|------|-------|
| `__` | 系统表（应用内部使用） | `__settings`、`__query_history` |
| 无前缀 | 用户表（用户创建） | `sales_data`、`user_info` |

### 5.4 为什么查询需要缓存？

**目标**: 提升重复查询的响应速度

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| **容量** | 100 条 | LRU 缓存，超过容量自动淘汰最久未使用的 |
| **TTL** | 300 秒（5 分钟） | 缓存条目存活时间，超时自动失效 |
| **开关** | 开启 | 可通过 `configureQueryCache()` 动态调整 |
| **失效策略** | 写操作失效 | `INSERT/UPDATE/DELETE` 等写操作触发 `invalidate_all()` |

**缓存键**: `make_cache_key(sql, params) = "${sql.length}|${sql}|${params}"`

### 5.5 为什么需要虚拟滚动？

**问题**: 当列表数据量很大时（如查询历史 1000+ 条），直接渲染所有 DOM 节点会导致页面卡顿。

**解决方案**: 虚拟滚动（只渲染可见区域的条目）

| 场景 | 总条目数 | 可见条目数 | 性能提升 |
|------|----------|------------|----------|
| 查询历史 | 1000+ | ~5（视口高度 520px，每项 96px） | **200x** |
| 任务日志 | 500+ | ~9（视口高度 400px，每项 44px） | **55x** |

### 7.2 代码规范

#### Rust 代码规范

| 规范 | 说明 |
|------|------|
| **禁止 `.unwrap()`** | 生产代码中禁止直接使用 `.unwrap()`，必须使用 `.ok_or()` 或 `?` 进行错误处理 |
| **禁止 `print!`/`println!`** | 生产代码中禁止直接使用 `print!`/`println!`，必须使用 `log::info!`/`log::error!` 等日志宏 |
| **所有 SQL 走参数化查询** | 禁止字符串拼接 SQL，所有 WHERE 条件必须绑定参数 |
| **表名必须使用 `SqlIdentifier`** | 所有用户表名、列名必须通过 `SqlIdentifier` 封装，防止 SQL 注入 |

#### TypeScript 代码规范

| 规范 | 说明 |
|------|------|
| **禁止 `any` 类型** | 生产代码中禁止显式 `:any`，必须使用精确类型 |
| **禁止 `console.log`** | 生产代码中禁止 `console.log`，必须使用 `console.error` 或日志服务 |
| **统一 store import** | 所有 store 必须通过 `store/index.ts` 统一 export |

### 9.2 查询缓存（LRU + TTL）

| 项目 | 说明 |
|------|------|
| 所在文件 | `src-tauri/src/services/query_cache_service.rs` |
| 缓存结构 | `HashMap<String, QueryResult>` + LRU 驱逐 |
| 默认容量 | **100 条** |
| 默认 TTL | **300 秒（5 分钟）** |
| 默认开关 | **开启**（`enabled=true`） |
| 缓存键 | `make_cache_key(sql, params) = "${sql.length}|${sql}|${params}"` |
| 白名单判断 | `is_cacheable(sql)`：仅 `SELECT / PRAGMA / WITH` 开头 |
| 写操作失效 | `is_write_operation(sql)`：`INSERT/UPDATE/DELETE/DROP/ALTER/CREATE/REPLACE/TRUNCATE` 触发 `invalidate_all()` |
| 接入位置 | `commands/sql.rs::execute_sql`：命中缓存直接返回，执行成功后写回缓存 |
| 配置接口 | `configure(capacity, ttl_seconds, enabled)` — 运行时动态调整 |
| 统计接口 | `stats()` → `CacheStats { capacity, size, hits, misses, hit_rate, enabled }` |

## 十、常见问题（FAQ）

### 10.1 为什么启动很慢？

**可能原因**:
1. 首次启动需要创建系统表（13 张）
2. 需要加载 Vite dev server（开发模式）
3. 需要编译 Rust 代码（首次 `cargo build` 较慢）

**优化方案**:
- 使用 `React.lazy` 懒加载非首屏组件
- 使用 `get_startup_status` 单次调用聚合所有首屏数据
- 使用 ECharts / AG-Grid 懒加载

### 10.2 为什么查询很慢？

**可能原因**:
1. 数据量过大（超过 100 万行）
2. 没有创建索引
3. 查询缓存未命中

**优化方案**:
- 确保查询是 `SELECT/PRAGMA/WITH`（走 DuckDB 分析引擎）
- 为常用过滤字段创建索引
- 开启查询缓存（默认开启）

### 10.3 为什么仪表盘图表不显示？

**可能原因**:
1. 图表配置错误（x_axis / y_axis 配置不正确）
2. SQL 查询结果字段与图表配置不匹配
3. ECharts 配置归一化失败（旧数据 snake_case 未转 camelCase）

**优化方案**:
- 使用 `normalizeEChartsConfig()` 归一化 ECharts 配置
- 使用三层级降级渲染（config 直渲 → SQL 重新生成 → queryId 查找）
- 检查 `dashboardStore.ts` 中 `savedCharts` 加载时序

### 10.4 为什么应用会卡死？

**可能原因**:
1. 启动阶段 IPv4/IPv6 不匹配（Vite 监听 IPv6，WebView2 解析 IPv4）
2. 数据库锁竞争（调度器持有锁，前端请求阻塞）
3. 无限渲染循环（React useEffect 依赖项设置不当）

**优化方案**:
- 确保 Vite 监听 `0.0.0.0`（IPv4 + IPv6 双栈）
- 使用 `get_connection()` Mutex 保护数据库连接
- 检查 `DashboardItem.tsx` 中 `filterValuesKey` 依赖项
