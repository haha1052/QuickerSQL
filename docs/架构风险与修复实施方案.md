## 0. 已完成的关键性修复回顾

### 0.1 问题描述
`TaskScheduleEngine::run_forever` 独立线程的循环中，`conn`（持有全局 `DatabaseManager.active_connection` 的 `MutexGuard`）**作用域延伸到 `sleep(30s)` 之外**，导致前端在 `get_app_state` / `get_all_settings` / `load_workspace` 等命令中排队拿锁最长 30 秒 → **界面一直停在 Loading**。

### 0.2 修复方案（已实现）
把"获取连接 + 扫描 + 执行任务"抽成独立函数 `TaskScheduleEngine::scheduler_do_one_pass`，该函数**内部** `let conn = ...;`，在**函数返回时** `conn` 自动 drop → 锁释放；外层 `loop` 在**锁已释放**的状态下 `sleep`。

```rust
impl TaskScheduleEngine {
    pub fn run_forever(db_manager: SharedDatabaseManager, shutdown: Arc<AtomicBool>) {
        std::thread::spawn(move || {
            loop {
                if shutdown.load(Ordering::Relaxed) { return; }
                let effective_interval_secs =
                    Self::scheduler_do_one_pass(&db_manager, &shutdown);
                // ↓↓ 此处 conn 已被 drop，锁已释放，不再阻塞前端
                std::thread::sleep(Duration::from_secs(effective_interval_secs));
            }
        });
    }

    fn scheduler_do_one_pass(...) -> u64 {
        let conn = db_manager.get_connection().ok()?;
        // 读 settings → 扫描到期任务 → execute
        scan_interval_secs
    }
}
```

## 1. 架构风险全景图

### 1.1 风险分级
| 级别 | 定义 | 典型表现 |
|-----|------|---------|
| 🔴 **高危** | 会导致用户感知的卡死、数据不一致或功能不可用 | 启动卡死、死锁、长 SQL 阻塞所有命令、数据丢失 |
| 🟡 **中危** | 不阻塞主流程，但带来性能/维护/观测性问题 | 重复 `ensure_*`、错误被静默吞掉、死代码告警 |
| 🟢 **低危** | 代码可读性/可维护性问题 | 可见性不一致、注释/日志不清晰 |

## 2. 各风险点的修复方案（按优先级、分阶段）

### 阶段一 — ✅ 已完成（跨 sleep 持锁）
### 阶段二 — 🔴 风险 A + I：DatabaseManager 连接并发模型升级（**新增能力**）

#### 2.1 目标
把"全局 1 把 Mutex 锁"升级为"**同一进程内允许多个并发连接**"，但在 Rust 侧保持与底层 SQLite driver 的**线程安全**约束。

#### 2.2 方案 A-2：支持连接句柄克隆的 `Arc<Mutex<Connection>>` 模式（最小改动）

**现状（简化）**：
```rust
pub struct DatabaseManager {
    active_connection: Mutex<Option<Box<dyn DatabaseConnection>>>,
}
pub fn get_connection(&self) -> Result<MutexGuardConnection<'_>> {
    let guard = self.active_connection.lock()...;
    Ok(MutexGuardConnection { guard })
}
```
问题：全局**只有一把锁**，所有 `get_connection()` 返回都拿到同 1 个 guard 的不同借用；在任意借用的生命周期内，其他线程拿不到锁。

**改造**：把 `active_connection` 改为 `Arc<Mutex<Option<Box<dyn DatabaseConnection>>>>`，每次 `get_connection()` 都 `clone()` 一个独立的 `Arc`，各连接的 `Mutex` 互相独立。

```rust
pub struct DatabaseManager {
    drivers: Vec<Box<dyn DatabaseDriver>>,
    active_connection: Arc<Mutex<Option<Box<dyn DatabaseConnection>>>>,
}

impl DatabaseManager {
    pub fn new() -> Self { DatabaseManager { drivers: vec![], active_connection: Arc::new(Mutex::new(None)) } }

    pub fn connect(&self, driver_name: &str, path: &Path) -> Result<()> {
        // 保持原逻辑：通过 driver 连接成功后，写入 Mutex
    }

    /// 返回独立克隆的连接句柄：调用者之间不相互阻塞
    pub fn get_connection(&self) -> Result<MutexGuardConnection> {
        let cloned = self.active_connection.clone();
        let guard = cloned.lock().map_err(|e| DatabaseError::ConnectionFailed(e.to_string()))?;
        // ... check connected / return
    }
}
```
**注意**：这里的 `Arc<Mutex<...>>` 其实本质仍是"只有一把 Mutex"，**不能真正并发**。要真正并发需要依赖底层 SQLite driver 本身是否支持多连接。本项目的 SQLite driver 通过 `conn.execute()` 已经是线程不安全的（因为 SQLite 单连接不可跨线程共享）。

**正确方向 — A-3：连接池 / 每线程独立连接**（**引入新能力**）：
- 让 `DatabaseManager::get_connection()` 返回 `Box<dyn DatabaseConnection>`（**可跨线程移动**的、非引用持有式对象）；
- 使用 [`r2d2`](https://docs.rs/r2d2)（或者 SQLite `Connection` 自带 `Rc<RefCell>` / 线程局部存储）；
- 对于本项目的典型并发量（`前端命令 ~10 + 后台调度线程 1`），容量 `max_size = 4` 的池就够。

**简化路径 — A-4（推荐最小代价实现"长 SQL 不阻塞短命令"）**：
- 保留**主连接**为"短命令 / settings / workspace 小读写"服务；
- 新增**执行通道**：对于用户 SQL 执行（`sql.rs::execute_sql_cmd` / 自动化任务的 `refresh_chart` 分支），**打开一个新的临时 SQLite 连接**（由 driver 的 `connect()` 再次打开同一文件路径），执行完即关闭，不常驻。
- SQLite 原生支持多进程/多连接并发访问（通过文件锁 + WAL）。`journal_mode = WAL` 是关键，`services/project_service.rs` 中已有 `ensure_wal` 调用。
- **改动位置**：`database/traits.rs::DatabaseManager` 增加 `open_temporary_connection(&self)`；`commands/sql.rs` 与 `services/task_service.rs::dispatch` 中把长 SQL 调用改为走临时连接。

**优点**：
- 不需要引入 `r2d2` 等新依赖（降低学习成本）；
- 架构清晰："主连接（短命令） + 临时连接（长 SQL）"；
- 风险 B（调度线程持锁执行长 SQL）与风险 A（所有命令互相阻塞）一次解决。

**缺点**：
- 需要正确处理"临时连接失败"（文件不存在 / 权限问题）的失败降级路径；
- 临时连接的生命周期必须被 `RAII drop` 管理，避免泄漏。

#### 2.3 方案 I-2：Mutex 中毒恢复（**小改动、高收益**）

**文件**：`src-tauri/src/database/traits.rs::DatabaseManager::get_connection`

**现状**：
```rust
pub fn get_connection(&self) -> Result<MutexGuardConnection<'_>> {
    let guard = self.active_connection.lock().map_err(|e| DatabaseError::ConnectionFailed(e.to_string()))?;
    guard.as_ref().ok_or(DatabaseError::DatabaseClosed)?;
    Ok(MutexGuardConnection { guard })
}
```

**改造**：匹配 `LockResult` 的 `Ok/Err`，在 `Err(poisoned)` 时**自动恢复**：
```rust
pub fn get_connection(&self) -> Result<MutexGuardConnection<'_>> {
    let guard = match self.active_connection.lock() {
        Ok(guard) => guard,
        Err(poisoned) => {
            log::warn!("DB Mutex 被 poison（上一命令可能 panic），自动恢复到 poison 前状态");
            poisoned.into_inner() // 仍能拿到 guard，只是内容可能被部分写入
        }
    };
    guard.as_ref().ok_or(DatabaseError::DatabaseClosed)?;
    Ok(MutexGuardConnection { guard })
}
```

**原理**：Poison 只是"上次持有 guard 的线程 panic 了"的标记，不是数据损坏。对于 SQLite 这种文件级持久化，**数据库文件的一致性由 SQLite 自身保证**（事务 / 日志），Mutex poison 不会导致数据库文件损坏。自动恢复是安全的。

```typescript
async function invokeWithTimeout<T>(
  command: string,
  args?: InvokeArgs,
  timeoutMs = 15_000,
): Promise<T> {
  const controller = new AbortController();
  const timeout = setTimeout(() => controller.abort(), timeoutMs);
  try {
    return await invoke<T>(command, { ...args, signal: controller.signal });
  } catch (e) {
    if (e instanceof DOMException && e.name === 'AbortError') {
      throw new Error(`调用超时（${timeoutMs}ms）：${command}`);
    }
    throw e;
  } finally {
    clearTimeout(timeout);
  }
}
```

### 阶段四 — 🟡 风险 C：集中式系统表初始化 + 幂等锁（**减少重复 DB 调用**）

#### 4.1 目标
`ensure_*_table_exists` 只在进程启动 + 切换 Project 时跑一次；运行期所有命令**不再**重复调用。

#### 4.2 方案 C-2：集中初始化 + `OnceLock` 本地标识（**避免每次都访问 DB**）

**文件**：
- `src-tauri/src/lib.rs::TauriAppState::new()`
- `src-tauri/src/commands/*.rs`

**步骤**：
1. **在 `TauriAppState::new()` 中补齐系统表初始化**（当前已有部分，但缺少 `DashboardService::ensure_tables_exist` / `AppStateService::ensure_app_state_table_exists` / `ensure_workspace_tables_exist`）：
   ```rust
   // （在 lib.rs TauriAppState::new 里已有）
   let _ = MigrationService::run_legacy_table_migrations(&conn);
   let _ = DashboardService::ensure_tables_exist(&conn);
   let _ = AppStateService::ensure_app_state_table_exists(&conn);
   let _ = AppStateService::ensure_workspace_tables_exist(&conn);
   let _ = SettingsService::ensure_settings_table_exists(&conn);
   let _ = TaskService::ensure_tables_exists(&conn);
   let _ = QueryHistoryService::ensure_query_history_table_exists(&conn);
   let _ = AuditLogService::ensure_audit_log_table_exists(&conn);
   let _ = TrashService::ensure_trash_table_exists(&conn);
   ```

2. **在 commands 层删除所有重复调用**：
   - `commands/settings.rs`（7 处 `ensure_settings_table_exists`）→ 全部删除；
   - `commands/app_state.rs`（`ensure_app_state_table_exists`、`ensure_workspace_tables_exist` 各数处）→ 全部删除；
   - `commands/dashboard.rs`（`DashboardService::ensure_tables_exist` 约 15 处）→ 全部删除；
   - `commands/automation.rs`（`TaskService::ensure_tables_exists`）→ 删除；保留**独立命令** `pub fn ensure_automation_tables(...)` 作为运维兜底；
   - `commands/query_history.rs`、`commands/audit_log.rs`、`commands/trash.rs`、`commands/sql.rs` 中对应 ensure 调用 → 全部删除。

3. **切 Project 的特殊路径**：`ProjectService::open_project` 切换到新文件后**必须重新跑一次**系统表初始化；在该函数内加 `ensure_all_system_tables(conn)`。

**为什么本方案能生效**：
- `CREATE TABLE IF NOT EXISTS` 是幂等的，但仍需要一次 SQLite 系统表访问（写入 sqlite_master 检查）；
- 把这步移到启动时一次性做完，后续每个命令都减少了 1 次"建表检查"的 round-trip；
- 以 `OnceLock` 做进程内二次保障（例如 `static INIT_DONE: OnceLock = OnceLock::new();` 再把 command 中的 ensure 调用加守卫），双重保险。

### 阶段五 — 🟡 风险 D：错误可观测性改造（`let _ =` 吞错清理）

#### 5.1 目标

- 失败至少打 `log::warn!`；

- **`src-tauri/src/services/task_service.rs`**：`scheduler_do_one_pass` 中的 `TaskService::ensure_tables_exists` 改为 `if let Err(e) = ... { log::warn!("确保自动化任务表失败: {}", e); return 30; }`；`execute()` 中的 `INSERT INTO __automation_runs` / `UPDATE tasks` / `UPDATE runs` 都加 `if let Err(e) = ... { log::warn!(...); }` 或 propagate 至外层返回值。
- **`src-tauri/src/lib.rs`**：`TauriAppState::new` 中的 `let _ = xxx_service::...(...)` 替换为 `if let Err(e) = xxx_service::...(&conn) { log::warn!("初始化 xxx 失败: {}", e); }`。

### 阶段七 — 🟡 风险 F：前端启动时的并发 invoke 改造（**允许并发，但加超时与降级**）

#### 7.1 目标
前端启动时同时发出 `get_all_settings`、`get_app_state`、`load_workspace` 三个 invoke，但**每一个都有超时 + 失败降级**，任何一个失败都不阻塞进入主界面。

#### 7.2 方案 F-2：`Promise.allSettled` + 超时守护

**文件**：`src/AppWrapper.tsx`

**改造前**：三个 invoke 并行但无超时。失败时 UI 停在 `isLoading = true`。

**改造后**：
```ts
useEffect(() => {
  (async () => {
    const { tauriService } = await import('./services/tauri');
    const timeout = 15_000; // 每个命令最多等 15 秒
    const [settingsResult, launchedResult] = await Promise.allSettled([
      invokeWithTimeout<...>('get_all_settings_cmd', undefined, timeout),
      invokeWithTimeout<...>('get_app_state', { category: 'welcome', key: 'has_launched' }, timeout),
      // workspace load 放后面，不阻塞首屏
    ]);
    // 处理 settingsResult / launchedResult 的成功/失败，统一写入 store
    setIsLoading(false);
    // 根据状态决定欢迎页 / workspace
  })();
}, []);
```

**文件**：`src/context/SettingsContext.tsx`
- `useEffect(() => { loadSettings(); }, [])` 增加 `if (categories.length === 0)` 守卫，不重复向 Rust 发命令；
- `loadSettings` 失败时仍让 UI 进入 workspace，settings 为空显示默认值。

### 阶段八 — 🟡 风险 G：`TaskService::execute` 事务化

#### 8.1 目标
一次 `execute` 内的 4 步操作（INSERT run → dispatch sql → UPDATE runs → UPDATE tasks）要么全部成功，要么全部回滚。

#### 8.2 方案
**文件**：`src-tauri/src/database/traits.rs::MutexGuardConnection`（已存在 `begin_transaction / commit_transaction / rollback_transaction`）
**文件**：`src-tauri/src/services/task_service.rs::execute`

```rust
pub fn execute(conn: &MutexGuardConnection<'_>, id: &str, trigger_type: &str) -> Result<TaskRun, String> {
    // 开启事务（SQLite 支持事务）
    conn.begin_transaction().map_err(|e| format!("开启事务失败: {}", e))?;

    // --- 原有 4 步 ---
    // 1. INSERT run (status='running')
    // 2. dispatch_sql(user_sql) 执行用户动作
    // 3. UPDATE runs (status='success' or 'failed')
    // 4. UPDATE tasks (last_run_at / next_run_at)
    // ----------------

    match exec_result {
        Ok(run) => {
            conn.commit_transaction().map_err(|e| format!("提交事务失败: {}", e))?;
            Ok(run)
        }
        Err(e) => {
            let _ = conn.rollback_transaction();
            Err(e)
        }
    }
}
```

**验收**：跑 `INSERT INTO nonexistent VALUES(1)` 的自动化任务 → 查 `__automation_runs`，不应出现 `status='running'` 的脏记录。

### 阶段九 — 🟡 风险 H：图表缓存字段跨端类型守护（**新增系统表 & 编译期对照表**）

## 5. 验收标准

每个阶段完成后必须满足：
1. **`cargo check`**：0 errors，`dead_code` / `visibility` 告警显著减少。
2. **`tsc --noEmit`**：0 errors；前端无新增 TS strict 告警。
3. **功能回归**：
   - 启动 → 欢迎页 → 工作区；
   - 新建自动化任务 → 立即运行 → 检查 `__automation_runs.status` 正确；
   - 新建 Dashboard + 图表 → 用自动化任务刷新 `last_result` → 前端跳过长 SQL 直接渲染；
   - 切 Project → 新 DB 文件的系统表在切换瞬间创建；
   - Settings 更新 → 立即生效；
   - QueryHistory / Trash / AuditLog 基础链路；
4. **性能基线**：冷启动 < 2s（Windows 开发机典型硬件）；"长 SQL 在跑"期间，打开设置页、切工作区等短操作 < 500ms 响应。
5. **架构自检**：对照 `AGENTS.md` 的"每次修改后强制检查清单"自检；系统表若新增，同步更新本文件第 3 节与 `AGENTS.md`。

## 6. 不做事项（防止无效改动）

- ❌ 不引入 `tokio` / `async-std` 等新的运行时 — Tauri 2.x 自身已有 `spawn` 能力；
- ❌ 不改变启动进程拓扑（仍由 Tauri 单进程承载前端 webview + Rust 后端）；
- ❌ 不删除 `DIAG` 代码前先跑一轮回归测试，确保能复现问题；
- ❌ 不把"系统表"改为前端 localStorage 持久化（双写会引入一致性问题）。

## 7. 回滚策略

任何一次阶段改动都必须**单步可逆**：
1. 每个阶段作为**独立 commit / 独立 PR**，commit message 含阶段编号与风险编号（如：`stage3: 集中式 ensure_* 初始化，删除 commands 重复 ensure [风险 C]`）；
2. 任何阶段导致 `cargo check` 或 `tsc --noEmit` 出现 error → **立即 `git revert`**，不带到下游；
3. 功能回归测试失败 → 回到该阶段前一个 commit，重新评审设计方案再推进。

## 8. 架构状态对比（Before / After）

### Before
```
前端 invoke
  ├─ get_app_state          ─┐
  ├─ get_all_settings       ─┼──> 抢同 1 把全局 DB Mutex
  └─ load_workspace         ─┘
调度线程 run_forever: { 拿锁 → 跑 SQL → sleep(30s 仍持锁) }
                                                   ↑ 前端全部阻塞
Task execute: { INSERT run → 执行用户 SQL（仍持锁） → UPDATE runs → UPDATE tasks }
                                           失败残留 status='running'
```

### After
```
前端 invoke（并发，但有超时 + 降级）
  ├─ getAllSettings      (拿主连接锁 → 读表 → 释放锁，超时 15s)
  ├─ getAppState         (拿主连接锁 → 读表 → 释放锁，超时 15s)
  └─ loadWorkspace       (拿主连接锁 → 读表 → 释放锁，超时 15s)
调度线程 scheduler_do_one_pass:
  { 拿锁 → 读 settings → 扫描到期任务 → 对"刷新图表 SQL"分支走临时独立连接 →
    写入结果 last_result / last_run_at → 函数返回（conn drop → 锁释放）→ sleep }
Task execute: { begin_transaction → insert_run → dispatch_sql → update_runs →
                update_tasks → commit; 失败 rollback，无脏数据 }
Mutex poison: { 某线程 panic 后，下一调用自动恢复，不影响前端 }
```
