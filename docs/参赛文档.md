## 1. Demo 简介

### 是什么
一款基于 **Tauri 2 + React + Rust** 开发的**本地桌面端数据分析与可视化工具**，无需联网、无需安装数据库，直接打开即可使用。所有数据存储在本地，保证安全性。

### 面向谁
- **数据分析师**：需要快速进行数据探索和分析的专业人员
- **业务人员**：需要查询业务数据但不会写复杂 SQL 的非技术用户
- **开发者**：需要本地数据库进行测试和开发的程序员
- **学生**：学习 SQL 和数据分析的初学者

## 2. Demo 创作思路

### 灵感来源
在日常工作中，我经常需要处理各种数据文件（CSV、Excel、Parquet），但每次都要先导入数据库才能进行分析，这个过程非常繁琐。我想要一个工具，能够直接打开数据文件，就能进行 SQL 查询和分析。

同时，我观察到很多业务人员有数据查询需求，但他们不会安装和配置数据库，也不会写复杂的 SQL。现有的数据库工具要么太重（如 DBeaver），要么功能不够（如 Excel）。

### 想解决的问题

**用户痛点 1：数据准备繁琐**
- 从 CSV/Excel 到可查询需要多个步骤：安装数据库 → 创建表 → 导入数据 → 编写查询
- 非技术用户无法完成这个流程
- **QuickerSQL 解决方案**：拖放文件即可导入，DuckDB 直接读取 Parquet/CSV 无需导入

**用户痛点 2：工具太重**
- 传统数据库工具（如 DBeaver）安装包大（200+MB）、启动慢、学习成本高
- 日常轻量数据分析不需要这么复杂的功能
- **QuickerSQL 解决方案**：Tauri 打包体积约 30MB，启动快，界面简洁

**用户痛点 3：SQL 能力门槛**
- 非技术用户不会写 SQL
- 即使会写，也经常忘记表名、列名
- **QuickerSQL 解决方案**：代码补全（表名、列名自动提示）、查询历史一键重执行

**用户痛点 4：数据可视化难**
- Excel 图表功能有限，BI 工具需要配置数据源
- 需要反复导出数据到可视化工具
- **QuickerSQL 解决方案**：内置仪表盘，SQL 查询直接生成图表，筛选器联动

**用户痛点 5：重复查询麻烦**
- 每天都要执行相同的查询（如日报数据）
- 手动执行容易遗漏
- **QuickerSQL 解决方案**：自动化任务，定时执行查询

**用户痛点 6：数据隐私安全**
- 在线数据分析工具需要上传数据到云端，存在隐私泄露风险
- **QuickerSQL 解决方案**：本地工具，数据不离开用户设备

### 为什么做这个方向

**判断和取舍：**

1. **选择本地而非在线**：数据安全是首要考虑，本地工具可以保证数据不离开用户设备

2. **选择双引擎（SQLite + DuckDB）**：
   - SQLite：事务支持好、写入快、成熟稳定（用于 INSERT/UPDATE/DELETE）
   - DuckDB：分析查询快（列式存储）、支持完整 SQL（CTE、窗口函数）、支持直接读取 Parquet/CSV
   - 根据 SQL 类型自动路由：SELECT → DuckDB，INSERT → SQLite

3. **选择 Tauri 而非 Electron**：
   - Tauri 打包体积更小（约 30MB vs Electron 的 200+MB）
   - 性能更好，内存占用更低
   - Rust 后端，安全性更高

4. **专注于核心功能**：
   - 不做报表制作（Excel/BI 工具已足够）
   - 不做数据清洗（Python/R 更专业）
   - 不做多用户协作（本地工具不需要）

5. **架构决策**：
   - 清晰的三层架构（commands → services → database）
   - 严格的安全约束（参数化查询、SqlIdentifier 校验）
   - 性能优化（查询缓存、虚拟滚动、代码分割）

## 附加部分：经验总结与踩坑复盘

### 经验总结

1. **自然语言描述需求是关键**：把需求描述清楚、具体，TRAE 才能生成高质量的代码。比如不要说"做一个查询历史"，而是说"查询历史应该显示最近的 SQL 查询，支持收藏、执行和删除，每条记录占一行，布局为：状态标记 | SQL 文本 | 收藏按钮 | 执行按钮 | 删除按钮"。

2. **先设计后实现**：在动手写代码之前，先用 TRAE 帮你设计架构和方案。这可以避免走弯路，也可以让你对整体有更清晰的认识。TRAE 帮我设计的架构规则文档（`.trae/rules/*.md`）成为了项目的"架构守护者"。

3. **遇到问题及时求助**：不要自己死磕，如果遇到问题，直接告诉 TRAE，它会帮你分析问题、找到解决方案。CSS 样式优先级问题我改了十几次都改不好，TRAE 一眼就看出了问题根因。

4. **测试验证很重要**：每次修改后，一定要用 TRAE 帮你验证（编译、测试），确保代码正确。TRAE 的编译门禁机制（cargo check + tsc --noEmit + vitest run）帮我拦截了很多潜在问题。

5. **架构约束让代码更规范**：TRAE 会自动遵循项目的架构规则（三层架构、禁止跨层调用、参数化查询等），这让我写的代码越来越规范，质量评分从最初的 6.0 提升到 8.9。

### 踩坑复盘

**坑 1：CSS 样式优先级问题**
- **问题**：按钮样式改了十几次都改不好，按钮还是很大
- **根因**：全局 CSS 的 `button:not(...)` 选择器特异性 `(0,1,1)`（1标签名+1伪类）高于组件 `button.btn-action` 的 `(0,2,0)`（2类名），全局规则优先级更高
- **解决方案**：用 `!important` 覆盖全局样式
- **TRAE 的帮助**：TRAE 帮我分析了 CSS 特异性、样式优先级，给出了详细的根因分析报告

**坑 2：DuckDB 参数化查询未实现**
- **问题**：DuckDB 的参数化查询没有正确处理，params 被忽略
- **根因**：代码中直接忽略了 params 参数，所有参数化查询都失败
- **解决方案**：实现 SQLite `?` 到 DuckDB `$1, $2` 的转换，正确绑定参数
- **TRAE 的帮助**：TRAE 在代码审查时发现了这个问题，并给出了修复方案

**坑 3：SQLite 扩展加载失败**
- **问题**：DuckDB 无法加载 SQLite 扩展，导致 ATTACH 失败
- **根因**：DuckDB 需要显式加载 SQLite 扩展，而本地编译时扩展下载可能被防火墙阻止
- **解决方案**：在代码中添加重试逻辑，尝试 INSTALL 和 LOAD 命令
- **TRAE 的帮助**：TRAE 帮我分析了 DuckDB 的扩展加载机制，给出了详细的技术报告

**坑 4：React 组件重渲染问题**
- **问题**：拖动分隔框时，列表项会反复重新渲染
- **根因**：flex 布局导致所有子元素重新计算位置
- **解决方案**：使用绝对定位分层布局，文本固定在底层，按钮固定在顶层
- **TRAE 的帮助**：TRAE 帮我分析了渲染链路，给出了分层布局的优化方案

**坑 5：查询缓存命中率低**
- **问题**：查询缓存命中率只有 20%，重复查询还是很慢
- **根因**：缓存键包含了 params，相同的 SQL 不同 params 无法命中
- **解决方案**：优化缓存键生成策略，区分有无 params 的场景
- **TRAE 的帮助**：TRAE 帮我设计了缓存命中率监控面板，实时追踪缓存效果
