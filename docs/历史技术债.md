## 二、v22.0 架构审计漏洞（50 项，2026-07-17 识别）

### 2.1 P0 级漏洞（5 项，历史已修复）

#### P0-1 | SQLite 缺少 `PRAGMA foreign_keys = ON`，外键约束形同虚设
- **位置**: `src-tauri/src/database/sqlite.rs:43-49, 71-77`
- **问题描述**: SQLite 连接初始化只设置了 `journal_mode=WAL`、`synchronous=NORMAL`、`cache_size`、`temp_store=MEMORY`、`busy_timeout=30000`，**没有设置 `PRAGMA foreign_keys = ON`**。这导致 `__dashboard_items` 表 DDL 中声明的 `FOREIGN KEY (dashboard_id) REFERENCES __dashboards(id) ON DELETE CASCADE` 完全不生效。
- **后果**:
  1. 删除 `__dashboards` 时不会自动级联删除 `__dashboard_items`（目前由代码手动删，但无事务保护，见 P1-6）
  2. 可插入不存在的 `dashboard_id` 到 `__dashboard_items`，造成孤儿数据
  3. 整个外键约束体系形同虚设
- **建议修复**: 在 `SqliteDriver::connect` 的 PRAGMA 初始化序列中追加 `PRAGMA foreign_keys = ON;`。**修复前需先排查现有孤儿记录**（开启外键后孤儿记录会变成"不可修改"）。

#### P0-2 | `batch_insert` 表名未走 SqlIdentifier 校验（潜在 SQL 注入）
- **位置**: `src-tauri/src/database/sqlite.rs:180-185` & `src-tauri/src/database/duckdb.rs:218-248`
- **问题描述**: `batch_insert` 使用 `format!("INSERT INTO \"{}\" ({}) VALUES ({})", table, ...)`，`table` 参数直接拼入 SQL，未经过 `SqlIdentifier::new()` 校验。虽然当前调用方（`commands/file.rs` 的 `import_data` 在 792、875 行）做了校验，但 `batch_insert` 作为公共 API 缺乏自我保护。DuckDB 版本更严重：值部分用 `v.replace('\'', "''")` 手工转义而非参数化。
- **建议修复**: `batch_insert` 内部强制要求传入 `&SqlIdentifier`，内部用 `ident.quoted()` 拼装；值统一用 `?` 占位符。彻底移除 DuckDB `batch_insert` 中的手工转义。

#### P0-3 | `format!` SQL 检测命令与规则文本自相矛盾
- **位置**: `.trae/rules/security.md §1.1` + `.trae/rules/CLAUDE.local.md §2.1` 的 PowerShell 检测命令 vs `.trae/rules/architecture.md §1.1 情形 C`
- **问题描述**: 检测命令期望 `Count = 0`，但实际测量 23 处；其中约 19 处是合法的 `format!("SELECT ... FROM {}", ident.quoted())` 用法（经 `SqlIdentifier` 封装），属于 architecture.md §1.1 "情形 C" 允许的写法。**规则文本允许、检测命令判违规**——规则自身矛盾，CI 门禁无法落地。
- **建议修复**: 修订检测命令用更精确的 regex 排除 `ident.quoted()` / `safe_xxx` 模式；或修订规则文本明确"经 SqlIdentifier 封装的 format! 调用允许"。

#### P0-4 | 前端大量硬编码中文未走 t() 函数（i18n 失效）
- **位置**: 跨 20+ 文件，代表性位置：
  - `src/components/dashboard/ChartLibraryPanel.tsx:118, 142, 161, 177-202, 321`
  - `src/components/dashboard/AddChartModal.tsx:48-142`（全部硬编码）
  - `src/components/dashboard/DashboardItem.tsx:401, 487, 500, 728, 753, 766, 772`
  - `src/components/dashboard/DashboardPage.tsx:146-176, 335-337, 445-451`
  - `src/components/common/ErrorBoundary.tsx:51, 58, 64`
  - `src/components/sql/hooks/useQueryExecution.ts:60, 88, 93`
  - `src/store/dashboardStore.ts:83, 105, 138, 157, 172, 190, 211, 230, 281, 314, 345`
  - `src/store/taskStore.ts:268-516`（共 20 处 toast 中文）
  - `src/store/projectStore.ts:129-227`
  - `src/store/tableStore.ts:112-203`
- **问题描述**: en-US 用户切换语言后仍看到大量中文残留，影响国际化体验。store 层错误消息硬编码尤其严重，因为 store 不在 React 树内无法直接调用 `t()`。
- **建议修复**:
  1. 在 LocaleContext 中扩展 i18n key 覆盖所有硬编码文案
  2. 对 store 层错误消息：引入 i18n store 订阅 locale 变化，或保存 error key 而非 message 由组件层翻译
  3. 建立 ESLint 规则禁止中文字符串字面量在 .tsx/.ts（除 LocaleContext 内）

#### P0-5 | `project_service.rs` 中 `__project_info` 表 CREATE TABLE 重复 5 次
- **位置**: `src-tauri/src/services/project_service.rs:341, 549, 974, 1080, 1691`
- **问题描述**: 同一份 schema 在 7 处维护（`__project_info` 5 次 + `__projects_registry` 2 次），任意字段变更需 7 处同步修改。line 1691 还用了 `CREATE TABLE`（无 IF NOT EXISTS），可能在高并发场景崩溃。
- **建议修复**: 提取 `ensure_project_info_table_exists()` 和 `ensure_projects_registry_table_exists()` 函数，所有调用点改为函数调用；line 1691 改为 `CREATE TABLE IF NOT EXISTS`。

### 2.2 P1 级漏洞（17 项，v23.0 全部修复）

#### P1-1 | `dashboard_service.rs` 大量 `format!` + `replace("'", "''")` 手工转义 [已修复 v23.0]
- **位置**: `src-tauri/src/services/dashboard_service.rs:248-296, 313, 352-374, 503-521, 694-704`
- **问题描述**: `save_query`、`create_saved_chart`、`refresh_saved_chart`、`create_dashboard` 等多处使用 `format!("... WHERE id = '{}'", id.replace("'", "''"))`。虽然 `'` → `''` 是 SQL 标准转义，但违反 security.md 强制要求的"必须参数化查询"规则，且无法应对多字节字符集边缘场景。
- **建议修复**: 全部改为 `"... ?"` + `&[&x]` 参数化形式。删除 `escape_sql_string` 工具函数。

#### P1-2 | `trash_service.rs` 回收站元数据操作手工转义 [已修复 v23.0]
- **位置**: `src-tauri/src/services/trash_service.rs:159, 166-172, 195-198, 240-243, 264-267, 298-301`
- **问题描述**: `__trash_metadata` 的 INSERT/SELECT/DELETE 均使用 `format!` + `replace("'", "''")`。回收站操作涉及表结构变更，一旦转义失效后果严重。
- **建议修复**: `__trash_metadata` 的所有写读删操作改为参数化查询。`ALTER TABLE` 部分维持 `SqlIdentifier` 方案。

#### P1-3 | `close()` 方法空实现，连接资源泄漏 [已修复 v23.0]
- **位置**: `src-tauri/src/database/sqlite.rs:171-172` & `src-tauri/src/database/duckdb.rs:215-216`
- **问题描述**: 两个驱动的 `close()` 方法体为空（`fn close(&mut self) {}`）。Drop 时机不可控，DuckDB 内存模式连接不释放会持续占用内存。`set_db_path` 切换数据库时旧 DuckDB 连接未显式释放。
- **建议修复**: `close()` 内部显式 `drop(self.conn.take())` 并记录日志。DuckDB 还需调用 `DETACH sqlite_db`。`set_db_path` 切换前先调用旧连接的 `close()`。

#### P1-4 | `execute_inner` 无事务保护，run 记录可能永久卡在 running [已修复 v23.0]
- **位置**: `src-tauri/src/services/task_service.rs:491-697`
- **问题描述**: `execute_inner` 流程：(1) INSERT run 记录（status=running）；(2) 执行 SQL；(3) UPDATE run 为成功/失败；(4) UPDATE task。四步不在事务内。若进程在 (1) 后崩溃，run 记录永远停留 running，下次启动后调度器的 `last_run_status != 'running'` 过滤会跳过该任务，任务被永久禁用。
- **建议修复**: (1) 启动时清理：`UPDATE __automation_task_runs SET status='failed' WHERE status='running'`；(2) run insert + run update 包在事务内；(3) task update 单独事务保证幂等。

#### P1-5 | 自动化任务调度器扫描与执行之间存在竞态 [已修复 v23.0]
- **位置**: `src-tauri/src/services/task_service.rs:1437-1467`
- **问题描述**: 调度器扫描 SQL 用 `last_run_status != 'running'` 过滤，但 `execute_inner` 只在 `__automation_task_runs` insert 时设 status=running，未同步更新 `__automation_tasks.last_run_status`。在 run insert 之前的窗口期，重复扫描会命中同一任务，导致同一任务并发执行两次。
- **建议修复**: `execute_inner` 开头立即 `UPDATE __automation_tasks SET last_run_status='running' WHERE id=? AND last_run_status != 'running'`，用乐观锁保证只有一个执行者进入。

#### P1-6 | `delete_dashboard` 未用事务 [已修复 v23.0]
- **位置**: `src-tauri/src/services/dashboard_service.rs:840-860`
- **问题描述**: `delete_dashboard` 执行两步：(1) DELETE FROM `__dashboard_items`；(2) DELETE FROM `__dashboards`。两步不在事务内。若 (1) 成功、(2) 失败，形成"空壳仪表盘"。
- **建议修复**: 用 `begin_transaction` / `commit_transaction` 包裹两步删除。配合 P0-1 修复外键后可改为仅 `DELETE FROM __dashboards`，依赖 `ON DELETE CASCADE`。

#### P1-7 | 事务方法各自独立加锁，无原子性保证 [已修复 v23.0]
- **位置**: `src-tauri/src/database/traits.rs:146-165`
- **问题描述**: `begin_transaction`/`commit_transaction`/`rollback_transaction` 三个方法各自调用 `lock_active_connection()` 获取独立锁，事务期间其他线程可以获取锁并 execute，破坏事务隔离性。
- **建议修复**: 重新设计事务 API：`begin_transaction` 返回 `TransactionGuard`，guard 持有 `MutexGuardConnection`，必须 drop guard 才能 commit/rollback。

#### P1-8 | `commands` 注册与 `capabilities` 严重不同步 [已修复 v23.0]
- **位置**: `src-tauri/src/lib.rs`（109 个 `#[tauri::command]`）vs `src-tauri/capabilities/default.json`（7 个 permissions）
- **问题描述**: `file-lock.md §三` 的"命令注册与权限同步"验证项期望"command 函数数量应与 capabilities 中注册的命令数一致"——实际 109 vs 7 严重不一致。注：Tauri 2 的 capabilities 主要用于插件权限（不强制声明自定义命令），但项目规则明确要求同步，规则未被遵守。
- **建议修复**: 明确规则与 Tauri 2 实际行为的差异；要么修订规则，要么补全 capabilities。

#### P1-9 | 前端 savedCharts 启动后长期为 Lite 版本，DashboardItem 全部渲染失败 [已修复 v23.0]
- **位置**: `src/store/dashboardStore.ts:464-487` 与 `src/components/dashboard/DashboardPage.tsx:191-214`
- **问题描述**: `setSavedChartsFromStartup` 将 SavedChart 映射为占位字段：`queryId: ''`、`sql: ''`、`config: null`、`lastResult: null`。DashboardPage 的 useEffect 只调用了 `loadDashboards()`，**完全没有调用 `loadSavedCharts()`**。DashboardItem 的 useEffect 触发条件是 `savedCharts.length === 0` 才加载，但启动后已填充 Lite 数据（length > 0），永远不会重新加载完整数据。结果：所有图表会展示"此图表数据不完整"错误。
- **建议修复**: 在 DashboardPage useEffect 内无条件触发 `loadSavedCharts()` 用完整数据覆盖 Lite 版本；或在 DashboardItem 内基于 `savedChart.sql === ''` 判断 Lite 状态触发刷新。

#### P1-10 | `dashboardStore` 单一 loading / error 字段被并发操作互相覆盖 [已修复 v23.0]
- **位置**: `src/store/dashboardStore.ts:5-10` 及所有 action
- **问题描述**: 所有 action 共享同一个 `loading: boolean` 和 `error: string | null`。用户在 loadDashboards 进行中点击 addChartToDashboard，后者会清掉前者的 loading；任一 action 失败，error 也会被后续成功 action 清空，导致前端丢失错误提示。
- **建议修复**: 参考 `taskStore.ts` 的 `loadingAction + loadingTaskId` 设计，改为按 action 名+资源 ID 维度的 loading 字典。

#### P1-11 | `addChartToDashboard` 二次 getDashboard 失败时仍返回 true [已修复 v23.0]
- **位置**: `src/store/dashboardStore.ts:267-279`
- **问题描述**: addChartToDashboard 成功后调用 `getDashboard` 刷新 store。若 getDashboard 失败，代码进入 `set({ loading: false }); return true;` 分支——返回 true 表示成功，但 store 中 dashboards 仍是旧数据，UI 显示成功 toast 但界面看不到新图表。
- **建议修复**: 二次 getDashboard 失败时返回 `false` 或显式 toast "添加成功但刷新失败，请手动刷新"；或保留乐观更新（用 addChartToDashboard 返回数据局部更新 layout）。

#### P1-12 | `ChartLibraryPanel` useEffect 依赖项不全且守卫错误 [已修复 v23.0]
- **位置**: `src/components/dashboard/ChartLibraryPanel.tsx:61-65`
- **问题描述**: `if (open && savedCharts.length === 0) loadSavedCharts()` 缺失 `savedCharts.length`、`loadSavedCharts` 依赖。业务逻辑漏洞：当 savedCharts 已被 Lite 启动数据填充（length > 0），即使 `open === true` 也不会重新加载，授权数据可能陈旧（2026-07-17 修复了字段缺失但未去掉 length 守卫）。
- **建议修复**: 改为 `if (open) loadSavedCharts()` 每次打开都刷新；或新增 "已加载完整数据" 标志位（基于 `savedCharts[0]?.sql` 是否为空判断）。

#### P1-13 | 多个 dashboard 组件订阅整个 store，导致级联 re-render [已修复 v23.0]
- **位置**:
  - `src/components/dashboard/DashboardItem.tsx:371`
  - `src/components/dashboard/DashboardPage.tsx:14-24`
  - `src/components/dashboard/DashboardCanvas.tsx:27`
  - `src/components/dashboard/ChartLibraryPanel.tsx:31-41`
  - `src/components/dashboard/AddChartModal.tsx:17`
- **问题描述**: 全部用 `const { xxx, yyy, ... } = useDashboardStore()` 解构，**没有 selector 函数**，订阅了整个 store。任一字段变化（如 loading、error、selectedChartId）都触发 re-render。DashboardItem 通常一个仪表盘 5-10 个，selectedChartId 变化会触发所有 DashboardItem 重渲染。
- **建议修复**: 使用 Zustand 的 shallow selector：`useDashboardStore(s => s.savedCharts.find(c => c.id === item.chartId))` 或 `useShallow`。

#### P1-14 | `ErrorBoundary` 仅在 SettingsWrapper 内部一层包裹 [已修复 v23.0]
- **位置**: `src/AppWrapper.tsx:551-567`
- **问题描述**: ErrorBoundary 包裹在 SettingsProvider/ThemeProvider/LocaleProvider 内部。若 SettingsProvider 自身渲染抛错（如 SettingsContext 默认值异常），ErrorBoundary 无法捕获，整个应用白屏。ThemeProvider、ThemeSettingsSync、CacheSettingsSync、AdvancedSettingsSync 都在 ErrorBoundary 之外。
- **建议修复**: 在最外层（`<AppWrapper>` 的 return 顶部）再加一层 ErrorBoundary 作为兜底。

#### P1-15 | `tauriService.invokeCommand` 用 `String(error)` 丢失堆栈 [已修复 v23.0]
- **位置**: `src/services/tauri.ts:70-83`
- **问题描述**: `String(error)` 对 Error 对象只会得到 `"Error: message"`，丢失 stack。所有 store 的 catch 块也是 `set({ error: String(e) })`，开发定位困难。
- **建议修复**: 保留 error 为 Error 对象，或日志中记录 `error.stack`；前端展示时再格式化。

#### P1-16 | `create_view` 的 `source_sql` 直接拼接，无多语句防护 [已修复 v23.0]
- **位置**: `src-tauri/src/services/database_service.rs:382`
- **问题描述**: `format!("CREATE VIEW {} AS {}", ident.quoted(), source_sql)` 中 `source_sql` 是用户输入的 SELECT 语句，直接拼入 DDL，没有任何校验。若用户传入 `"SELECT 1; DROP TABLE __saved_charts"`，多语句执行行为可能导致意外。
- **建议修复**: (1) 禁止 `source_sql` 包含 `;`（除末尾）；(2) 禁止以非 SELECT/WITH 开头；(3) 正则排除 `DROP|DELETE|INSERT|UPDATE|ALTER|CREATE|ATTACH|DETACH` 关键字出现在语句开头。

#### P1-17 | `add_chart_to_dashboard` 服务层未校验图表可见性 [已修复 v23.0]
- **位置**: `src-tauri/src/services/dashboard_service.rs:957-1006`
- **问题描述**: 服务层仅校验 chart_id 和 dashboard_id 是否存在，未校验该 chart 的 `visibility` 和 `authorized_dashboard_ids`。前端 `ChartLibraryPanel.isChartAvailableTo` 校验可被绕过（直接调用 IPC 即可把 restricted 图表加到非授权仪表盘）。
- **建议修复**: 在 `add_chart_to_dashboard` 服务层增加校验：若 visibility='restricted' 且目标 dashboard_id 不在 authorized_dashboard_ids 中，返回错误。前端校验仅作 UX 优化，服务层是安全边界。

### 2.3 P2 级漏洞（18 项，v23.0 全部修复）

#### P2-1 | `fast_import_csv/parquet` 路径手工转义 [已修复 v23.0]
- **位置**: `src-tauri/src/services/database_service.rs:538-557, 582-585, 609-613`
- **问题**: `COPY ... FROM '{}'` 和 `SELECT * FROM parquet_scan('{}')` 中文件路径用 `path.replace('\\', "\\\\").replace('\'', "''")` 手工转义，可能与 DuckDB 解析器存在不一致。
- **建议修复**: DuckDB 支持 `read_csv_auto(?)` / `read_parquet(?)` 参数化形式，改为参数化查询。

#### P2-2 | `init_duckdb` 的 ATTACH 路径手工转义 [已修复 v23.0]
- **位置**: `src-tauri/src/lib.rs:344`
- **问题**: `format!("ATTACH '{}' AS sqlite_db (TYPE SQLITE);", sqlite_path_str.replace("'", "''"))`。`sqlite_path_str` 来源受项目内部管理，风险较低，但违反"禁止 format! 拼 SQL"规则。
- **建议修复**: DuckDB 的 ATTACH 支持参数化（`ATTACH ? AS sqlite_db`），改为参数化形式。

#### P2-3 | `init_duckdb` 创建 VIEW 不在事务内 [已修复 v23.0]
- **位置**: `src-tauri/src/lib.rs:322-389`
- **问题**: 为每张 SQLite 表创建同名 VIEW，多个 CREATE VIEW 独立执行不在事务内。若中途某张表 VIEW 创建失败，DuckDB 处于半初始化状态，下次查询时部分表可用、部分不可用。
- **建议修复**: 将所有 CREATE VIEW 包在 DuckDB 事务内；失败时 ROLLBACK 并返回明确错误。

#### P2-4 | DuckDB 视图未找到时触发 `refresh_all_views` 重试，可能造成显著延迟 [已修复 v23.0]
- **位置**: `src-tauri/src/services/sql_service.rs`
- **问题**: 当查询命中 DuckDB 但 VIEW 不存在时，`sql_service` 会调用 `refresh_all_views` 重建所有视图后重试。在 schema 含数百张表时，重建所有 VIEW 可能耗时数秒，用户单次查询被放大数倍延迟。
- **建议修复**: 维护"已创建 VIEW 集合"，只对缺失的表增量创建；重建异步进行，查询先返回友好错误。

#### P2-5 | `get_connection_with_timeout` 的 50ms 轮询在长查询下效率低 [已修复 v23.0]
- **位置**: `src-tauri/src/database/traits.rs:244-268`
- **问题**: `try_lock` + `sleep(50ms)` 循环等待连接。长查询持锁数秒时，等待方频繁醒来又睡去，浪费 CPU。
- **建议修复**: 用 `Condvar` 替代 sleep 轮询；或采用连接池模式（`r2d2`）；至少改为指数退避（50ms → 100ms → 200ms ... 上限 1s）。

#### P2-6 | `trigger_downstream_tasks` 无事务 [已修复 v23.0]
- **位置**: `src-tauri/src/services/task_service.rs:1168-1224`
- **问题**: 上游任务完成后遍历下游任务执行 UPDATE，多个下游任务的更新不在事务内。若中途某个 UPDATE 失败，部分下游被触发、部分未触发，链式自动化流程断裂且无法回滚。
- **建议修复**: 将所有下游 UPDATE 包在事务内；任一失败则 ROLLBACK 并记录日志。

#### P2-7 | 回收站还原未预检表名冲突 [已修复 v23.0]
- **位置**: `src-tauri/src/services/trash_service.rs:225-245`
- **问题**: `restore_from_trash` 直接执行 `ALTER TABLE ... RENAME TO ...`。若原表名已被新表占用，`RENAME TO` 会失败，错误信息为 SQLite 原生错误，对用户不友好。trash 表状态未变更，用户可能误以为还原成功。
- **建议修复**: 还原前先 `SELECT name FROM sqlite_master WHERE type='table' AND name=?` 检查；若已被占用，返回友好错误；可选支持"还原为其他名称"参数。

#### P2-8 | `ChartLibraryPanel` 虚拟滚动 absolute 定位与 expanded 高度冲突 [已修复 v23.0]
- **位置**: `src/components/dashboard/ChartLibraryPanel.tsx:231-313`
- **问题**: 虚拟滚动用 `position: absolute; top: indexToOffset(actualIndex, CHART_ITEM_HEIGHT)`，但选中项用 `CHART_ITEM_EXPANDED_HEIGHT`（280）而非 `CHART_ITEM_HEIGHT`（96）。被选中项之后的图表位置仍按 96 计算，与选中项的展开区域重叠。
- **建议修复**: 选中项展开时动态调整后续项 offset；或采用变高虚拟滚动库（`@tanstack/react-virtual`）。

#### P2-9 | `DashboardItem` ChartCanvas ECharts 在主线程渲染大数量数据 [已修复 v23.0]
- **位置**: `src/components/dashboard/DashboardItem.tsx:248-339`
- **问题**: ECharts 渲染、ResizeObserver 回调、`optimizeConfigForSize`（含 JSON.parse/stringify）全部在主线程。仪表盘 6+ 图表且每个数据点超过 1000 时，编辑模式拖拽会触发 ResizeObserver 频繁回调。
- **建议修复**: 用 Web Worker 处理 `optimizeConfigForSize`；或缓存优化后的配置，仅在尺寸跨阈值变化时重新计算。

#### P2-10 | `SqlQueryPage` AgGrid rowData 每次渲染都重新构造 [已修复 v23.0]
- **位置**: `src/components/sql/SqlQueryPage.tsx:98-118, 180-200`
- **问题**: `rowData` 在每次 render 都通过 `.map` 重新构造，row data 引用每次都不同，AG-Grid 会全量刷新。
- **建议修复**: 用 useMemo 缓存 rowData 和 columnDefs；添加 `getRowId` 提供稳定 ID。

#### P2-11 | `DashboardItem` `optimizeConfigForSize` 用 `JSON.parse(JSON.stringify(config))` [已修复 v23.0]

#### P2-12 | IPC 错误无重试机制 [已修复 v23.0]

#### P2-13 | `alert/confirm` 阻塞 UI 且样式不一致 [已修复 v23.0]

#### v25-P0-1 | DuckDB `query` 方法忽略 `_params` 参数，参数化查询在分析路径完全失效 ✅ 已修复 v25.1
- **位置**: [src-tauri/src/database/duckdb.rs:93](file:///e:/LA_DUCK/la-duck/src-tauri/src/database/duckdb.rs#L93)
- **问题描述**: `DuckDbConnection::query` 方法签名接收 `_params: &[&dyn ToSql]`，但方法体内完全忽略该参数，直接 `stmt.query_arrow([])` 以空参数执行。这意味着所有走 DuckDB 路径的查询（分析型 SQL，包括 GROUP BY/JOIN/窗口函数等）的参数化绑定完全失效。虽然当前调用方多数传 `&[]`，但作为 DatabaseConnection trait 的实现，这是接口契约违背。
- **后果**: 任何未来通过 DuckDB 路径传递参数的查询将静默丢失参数，可能导致查询结果错误或 SQL 注入风险。
- **建议修复**: 将 `stmt.query_arrow([])` 改为 `stmt.query_arrow(params_refs)`，其中 `params_refs` 参照 `execute` 方法的转换逻辑（第 84-87 行）从 trait `ToSql` 转为 duckdb `ToSql`。需注意类型保持（见 v25-P1-1）。
- **修复状态**: ✅ 已修复 v25.1 — `stmt.query_arrow([])` 已改为正确绑定参数的 `stmt.query_arrow(params_refs)`，与 `execute` 方法的参数转换逻辑保持一致。

#### v25-P0-2 | 密码保护使用 `btoa()` Base64 编码而非加密哈希 ✅ 已修复 v25.1
- **位置**: [src/App.tsx:159](file:///e:/LA_DUCK/la-duck/src/App.tsx#L159)、[src/App.tsx:166](file:///e:/LA_DUCK/la-duck/src/App.tsx#L166)
- **问题描述**: 应用锁定密码使用 `btoa(passwordInput)` 进行"哈希"，但 `btoa` 是 Base64 编码，完全可逆。攻击者获取 localStorage 后可立即反解出明文密码。哈希存储在 `localStorage`（App.tsx:93, 160），可被同源脚本读取。注释 `// 简化实现，生产环境应使用更安全的哈希` 承认问题但未修复。
- **后果**: 本地攻击者（如恶意浏览器扩展）可轻松获取用户锁定密码。
- **建议修复**: 使用 Web Crypto API `crypto.subtle.digest('SHA-256', ...)` + 随机 salt；salt 与 hash 都存 localStorage；考虑 PBKDF2 增加暴力破解成本。
- **修复状态**: ✅ 已修复 v25.1 — 密码保护从 `btoa()` 升级为 SHA-256+salt 哈希方案，包含自动迁移逻辑（检测到旧 btoa 编码时自动转换为新格式存储）。

### 8.2 P2-3 前端 SQL 检测规则修订（误报 1744 → 0）

**修复日期**: 2026-08-20
**修复版本**: v26.2

**修复内容**: 修订前端 SQL 检测规则（v26.2 修订版），采用 case-sensitive 匹配 + 排除 SQL 客户端工具类目录 + safe_sql 白名单机制。

**修订要点**:

1. **case-sensitive 匹配**：原规则 `-CaseSensitive:$false` 会匹配 `<select>` HTML 元素、`selection` 变量等非 SQL 关键字。改为 `-CaseSensitive` 后只匹配大写的 SQL 关键字。

2. **排除 SQL 客户端工具类目录**：QuickerSQL 是 SQL 客户端工具，以下目录中的 SQL 关键字属正常业务用法：
   - `src/components/sql/`（SQL 编辑器、SQL 结果网格、SQL hooks 等所有 SQL 组件）
   - `src/utils/sql*`（SQL 工具函数：解析、转换、补全、格式化）
   - `src/utils/resultCopy`（SQL 结果复制：含 INSERT 模板生成、表名提取）
   - `src/context/LocaleContext.tsx`（i18n 文案中的 SQL 示例）
   - `src/__tests__/`、`*.test.ts`、`*.test.tsx`（测试文件中的 SQL 测试数据）

3. **safe_sql 白名单**：对剩余的合法用例（如 form placeholder 中的 SQL 示例、SQL 关键字检测逻辑、SQL 客户端工具生成的 SQL 模板）使用 `// safe_sql:` 注释标记白名单（与 Rust 侧机制一致）。

**同步修订的规则文件**:
| 文件 | 修订位置 | 修订内容 |
|------|---------|---------|
| `.trae/rules/security.md` | 前端 SQL 拼接检测章节 | 增加 v26.2 修订说明 + 新检测命令 |
| `.trae/rules/CLAUDE.local.md` | §2.2 前端禁止拼接 SQL | 同步检测命令 + 明确允许的目录和白名单机制 |
| `.trae/rules/mcp.md` | §十二 MCP 工具验证命令汇总表 | 更新前端 SQL 拼接检测命令 |

**修订后的检测命令**:
```powershell
Get-ChildItem -Path src -Include *.ts,*.tsx -Recurse -File |
  Where-Object {
    $_.FullName -notmatch '\\components\\sql\\' -and
```
