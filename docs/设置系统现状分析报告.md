## 六、快捷键设置实施难度分析

### 6.1 为什么之前没实施？

#### 原因 1：复杂度被低估

快捷键看似只是"把硬编码改成从设置读取"，但实际上涉及：

- **全局快捷键系统**：应用级别的快捷键（如新建、打开、设置）需要独立于编辑器的快捷键系统
- **Monaco 编辑器快捷键**：编辑器内的快捷键需要通过 Monaco 的 API 来配置，不能简单地用 DOM 事件
- **冲突检测**：用户自定义快捷键时，可能与现有快捷键冲突，需要检测和提示
- **跨平台兼容**：Windows/Linux 用 Ctrl，macOS 用 Cmd，需要统一处理
- **快捷键序列化**：如何存储和展示快捷键组合（如 Ctrl+Shift+F）

#### 原因 2：需要完整的架构

不能只是简单地把硬编码改成从设置读取，需要一个完整的快捷键管理系统，包括：

- 快捷键注册表：统一管理所有快捷键
- 快捷键配置读取：从设置系统加载用户自定义快捷键
- 冲突检测机制：检测并提示快捷键冲突
- 快捷键 UI：让用户直观地修改和重置快捷键

#### 原因 3：优先级问题

- 之前的 Phase 都在做高优先级的功能设置（编辑器、SQL 查询、数据导入等）
- 快捷键属于体验优化类，优先级相对较低
- 但 20 项全是空壳，已经影响到用户信任，需要提上日程

---

### 6.2 技术方案对比

#### 方案 A：Monaco 内置快捷键 + 全局快捷键混合

**思路：**
- 编辑器内快捷键：继续用 Monaco 内置的 `addCommand` / `addAction`，但从设置读取快捷键值
- 全局快捷键：用 Tauri 的全局快捷键 API 或 React 层面的键盘事件

**优点：**
- Monaco 自带的快捷键机制成熟稳定
- 改动相对较小，不需要完全重构
- 编辑器内快捷键体验有保障

**缺点：**
- 全局快捷键需要单独实现，两套机制并存
- 冲突检测困难（编辑器内和全局的冲突）
- 扩展性较差，未来新增快捷键需要改两处

**工作量：** 中高（约 5-7 天）

---

#### 方案 B：统一快捷键管理系统

**思路：**
- 建立统一的快捷键管理层（ShortcutManager）
- 所有快捷键（编辑器内 + 全局）都通过统一的接口注册和绑定
- 统一的冲突检测、配置读取、持久化

**优点：**
- 统一管理，架构清晰
- 支持完整的冲突检测
- 扩展性好，未来新增快捷键很方便
- 用户体验一致

**缺点：**
- 实现复杂度高
- 需要封装 Monaco 快捷键 API
- 初期工作量大

**工作量：** 高（约 8-12 天）

---
