### 问题2：视觉样式修改后保存不生效（多轮修改都存不下来）

**排查链路**（逐层验证均正常）：`ChartVisualFullEditor.updateField`（用 ref 避免陈旧闭包）→ `ChartEditSidebar.setVisualConfig` → `store.updateSavedChart` cleaned 参数 → `tauriService.updateSavedChart` 的 `args.visual_config` → Rust `update_saved_chart` 命令解析 → `DashboardService::update_saved_chart` 的 UPDATE 语句 → `row_to_saved_chart` 回读。**后端读写链路完全正常**。

**根因在前端** `ChartEditSidebar.tsx`：

```ts
// 旧实现（有问题）
const setVisualConfig = useCallback((config: VisualConfig) => {
  setVisualConfigState(config);
  updateSavedChartLocal(chart.id, { visualConfig: config });  // ← 立即污染持久化数据
}, [chart.id, updateSavedChartLocal]);
```

引发两个连锁 Bug：
1. **`hasChanges` 恒为 false** —— L174 比较 `visualConfig !== chart.visualConfig`，但 store 已被同步成同一个值，导致"有未保存的修改"提示永不出现，用户看不到任何未保存信号
2. **保存后样式被清空** —— `updateSavedChart` 成功后 store 条目被后端返回值整体替换，`updatedAt` 变化 → `chartSyncKey` 变化 → 触发 L129 的重置 effect → `setVisualConfigState(chart.visualConfig || {})`。视觉上表现为"保存后修改丢失"

**修复方案**：引入**预览通道**（preview draft），把"实时预览"与"持久化数据"彻底分离。

改动文件：
1. `src/store/dashboardStore.ts` —— 新增 `previewVisualConfigs: Record<chartId, config>` 状态 + `setVisualConfigPreview` / `clearVisualConfigPreview` 两个 action；`resetForProjectSwitch` 中一并清空（防跨项目 chartId 碰撞串样式）
2. `src/components/dashboard/ChartEditSidebar.tsx` —— `setVisualConfig` 改为只写本地 state + 预览通道；挂载/卸载时清草稿；`handleSave` 成功后清草稿
3. `src/components/dashboard/DashboardItem.tsx` —— 新增 `effectiveVisualConfig` memo：草稿优先，回退 `savedChart.visualConfig`
4. `src/__tests__/visualConfigPreview.test.ts` —— 新增 6 个回归测试

**关键设计原则（可复用）**：编辑器需要实时预览、但不能污染持久化数据时，必须用独立的 preview 通道承载草稿，而不是直接写 store 的业务字段。

## 问题2 第二轮修复（真正的根因）

第一轮修复后用户反馈"还是没有解决"，并提供启动日志。日志关键证据：

```
[CMD] update_saved_chart: visual_config raw = None
[SVC UPDATE] visual_config is None — SKIPPING UPDATE for this column!
[SVC UPDATE] UPDATE executed SQL columns: updated_at, name, title, tags, description, config, visibility, sql
```

**根因（一句话）**：`tauri.ts` 的 `updateSavedChart` 向 `invoke` 传递了 **snake_case 扁平参数**（`chart_type`/`x_axis`/`y_axis`/`visual_config`/`authorized_dashboard_ids`），而 **Tauri v2 的 `#[tauri::command]` 只接受 camelCase 键**。单词参数（name/title/tags/description/config/visibility/sql）两种命名恰好一致所以侥幸通过；5 个多词参数被 serde **静默丢弃**（未知键不报错，直接 `Option::None`）→ 服务层跳过对应 UPDATE 列 → DB 保留旧值。保存后 `updatedAt` 变化触发 `chartSyncKey` 重置 effect 用旧值回填编辑器 → 用户看到"修改被保存键清除"。

**定位方法**：对比 UPDATE 实际执行的 8 列与传入的 11 个字段，发现缺失的 5 个全是多词 snake_case、进入的 7 个全是单词 —— 命名约定不匹配的指纹特征。交叉验证：`createSavedChart` 全部用 camelCase（且注释里写明了该契约），创建图表一直正常；代码库其他命令（filePath/projectId/tableName/oldTableName…）也全是 camelCase。

**修复**（纯前端，Rust 无需改动——命令本就按 camelCase 接收）：
1. `src/services/tauri.ts` L1056-1076：5 个参数改为 camelCase（`chartType`/`xAxis`/`yAxis`/`visualConfig`/`authorizedDashboardIds`），补充注释说明历史 bug 防回归
2. `src/components/dashboard/ChartEditSidebar.tsx`：`chartSyncKey` 重置 effect 移除 `setActiveTab('basic')` —— 用户在 visual 标签页保存后应停留在当前页看到已保存结果，而不是被踢回 basic 页（加剧了"修改被清除"的错觉）
3. `src/__tests__/updateSavedChartArgs.test.ts`：新增 3 个回归测试锁定 camelCase 契约（断言 camelCase 键存在 + snake_case 键不存在）

**验证**：tsc 0 errors；vitest **203 passed**（含新增 3 个）；i18n 严格门禁 167 处 = 修复前基线（无新增）；vite build 42.95s 成功。

**可复用经验**：
- **Tauri v2 命令参数必须是 camelCase**（Rust 侧 snake_case 由宏自动转换）。写 invoke 参数时逐字核对，单词参数会掩盖错误，只有多词参数才暴露——这类 bug 靠"功能看起来一半 Work"暴露，极易漏检。
- 排查"保存丢失"类问题：**对比后端实际收到的字段与前端传参的差异，看缺失字段的命名特征**（全多词 = 命名约定问题；全某功能字段 = 分支逻辑问题）。

## 问题5：修改图表类型预览无响应、保存后也不生效（2026-10-23 第三轮）

**根因**：`SavedChart.config` 是「SQL 结果 × chartType × 坐标轴」的**派生缓存**，DashboardItem 渲染优先级为 **config 直渲 > SQL 重新生成**（L532 的 lastResult 缓存路径仅自动化任务会写入 last_result，普通图表为 null，直接跳过）。因此只要 config 存在就永远直渲旧 config —— 侧边栏改 chartType/xAxis/yAxis 只更新这些字段（原有 syncTimer effect 会写 store），但直渲的 config 不变 → 预览无响应；`handleSave` 持久化的也是旧 config（`config: chart.config`）→ 重启后依然是旧图表。**SQL 编辑同理受损**（查询 tab 提示"修改后需保存才能生效"，实际保存后旧 config 仍然优先直渲）。

**修复**（`src/components/dashboard/ChartEditSidebar.tsx`）：
1. 新增 `regenerateConfig({chartType, xAxis, yAxis, sql})`：重新执行图表 SQL → `generateChartConfig` 生成新 config → `updateSavedChartLocal` 写入 store（预览即时生效）。带 `regenSeqRef` 序列号防快速连续修改的竞态（过期结果丢弃）；查询失败/为空时保留原 config 不破坏渲染
2. 扩展原 sync effect：`changedFields` 增加 `sql`（600ms 防抖）；任一输入变化时 `doSync` 除写字段外一并调用 `regenerateConfig`
3. `handleSave` 保存前先用当前输入重建 config 并以返回值持久化（`config: freshConfig ?? chart.config`）—— 防止 debounce 未触发/异步竞态导致旧 config 落库

**关键架构认知（可复用）**：派生缓存（config）必须随其生成输入（chartType/坐标轴/SQL）的变化而失效重建，否则"改输入不生效"会以各种形态出现（预览不响应、保存不生效、重启回退）。这类 bug 的特征是"字段明明存进去了但界面没变化"—— 要检查渲染链路是否有更高优先级的旧缓存短路了新值。

**验证**：tsc 0 errors；vitest 203 passed；i18n 167 处 = 基线；vite build 44.54s 成功。
