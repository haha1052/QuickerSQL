# 用户操作全流程缺陷调查 — 验证清单（Checklist）

> 验证调查报告的完整性与质量。通过标准：所有检查点勾选 [x]。

---

## 报告覆盖范围

- [ ] 1. 覆盖 10 个用户操作阶段（冷启动/项目/导入/查询/结果/图表/仪表盘/自动化/设置/错误恢复），每阶段有独立缺陷清单
- [ ] 2. 横向调查"跨功能数据流断链"5 条路径全部覆盖（导入→查询→图表→仪表盘→自动化→项目切换）
- [ ] 3. 3 类用户画像（数据分析师/业务运营/开发者）各有 Top-3 痛点

## 缺陷条目质量

- [ ] 4. 每条缺陷包含 5 维评估：①严重度(UX-P0~P3) ②触发条件 ③用户感知 ④根因文件 ⑤修复方向
- [ ] 5. 至少 70% 条目的根因文件有具体行号或函数名引用（不是泛泛说"导入组件有问题"）
- [ ] 6. 至少识别出 5 条 UX-P0 级缺陷（阻塞核心路径）
- [ ] 7. 每条缺陷标注与 engine-arch-assessment-v25.3 技术债的关联关系（如"对应 TD-P0-01"或"新发现"）

## 调查方法论

- [ ] 8. 调查基于代码静态分析（Read 源码）而非凭空推测，关键结论有代码引用
- [ ] 9. 调查包含启动日志分析（基于 [npm run tauri dev](file:///e:/LA_DUCK/la-duck/src-tauri/src/lib.rs) 日志中的 WARN/ERROR）
- [ ] 10. 调查回溯了已知问题（I-01~I-08 + 之前对话中"仪表盘添加图表失败"等）

## 用户体验评估深度

- [ ] 11. 包含 SUS 估计得分更新（与 engine-arch-assessment 的 71.2 对比，覆盖更广后是否变化）
- [ ] 12. 识别出至少 3 个"用户不知如何恢复"的场景（如永久损坏需重启、查询死循环、导入0行误导）
- [ ] 13. 识别出至少 2 个"用户不知功能存在"的场景（如参数化查询、SQL 代码片段、回收站）

## 报告可操作性

- [ ] 14. 产出 v25.4 修复建议清单，与引擎侧 v25.4 任务（TD-P0-01/02/03 + TD-P1-05）对齐
- [ ] 15. 每条修复建议有明确的"修复后用户旅程变化"描述（如"修复后用户从F级→D级"）
- [ ] 16. 报告不包含代码实施（纯调查，代码修改在后续独立 spec 中进行）

## 报告格式规范

- [ ] 17. 所有文件/函数引用使用 clickable link 格式（file:/// 绝对路径）
- [ ] 18. 缺陷编号统一格式（UX-DEF-NNN）
- [ ] 19. 报告语言与用户请求一致（中文）
- [ ] 20. 报告无自相矛盾（如同一缺陷在不同阶段被不同严重度标注）
